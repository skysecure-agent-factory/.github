Skysecure Engineering - Production Ready AI Agent Development Guide

Production-ready agents6 engineering phases25 accountable steps

Use this guide when building agents at Skysecure Engineering.

Build agents that protect client data, work in different client environments, recover from failures, and can be supported in production—not just shown in a local demo.

A local demo shows that an idea can work. Before production, prove that the solution works safely, handles repeated requests and the expected load, and runs in a fresh client environment.

This guide covers the full journey: understand the business need, design and build the agent, secure and test it, deploy it, monitor it, and recover from failures. Use the simplest safe design. Follow a conditional section when your agent uses that capability.

How developers use this guide

Use this guide while building and reviewing an agent. You do not need to read every page again for a small change, but you must still meet every requirement that applies to your project.

  1. Copy and complete Step 0. Confirm what your agent does and what it needs before choosing or reviewing the code.
  2. Follow the steps that apply. Use the applicability map and phase navigation to find the requirements for your agent.
  3. Save proof as you work. Keep test results, AI evaluations, configuration, deployment checks, and operating records with the project. Do not leave this until release time.
  4. Prepare the autodeployment handoff when needed, then complete the final production check. Make the release decision only when every applicable outcome has evidence. The handoff checklist is in Phase 6 for easy reference, but you must complete it before deployment—not after going live.

Important: Navigation links help you find a section. They do not let you skip any security, privacy, reliability, testing, or release requirement that applies to your agent.

Engineering path: PROFILE → DESIGN → BUILD → SECURE → TEST → HAND OFF → DEPLOY → OPERATE

Complete Step 0 before designing, generating, approving, or making a significant change to code. For an existing project, first inspect enough of the repository to confirm the project profile. Then begin the production review.

Publication control: This guide has one permanent public URL. Edit the main source file, docs/index.html in the organization documentation repository, on a task branch. Raise a pull request into prod and merge after the automated guide checks pass. The authorized owner controls publication; this documentation repository does not require a separate human approval.

Each merge into prod builds and publishes the guide through GitHub Actions and GitHub Pages. Saving a local file does not publish it, and your laptop does not need to stay online. Wait for deployment to finish. Visible guide pages check for updates at most once every five minutes; hidden tabs do not poll. Developers can also refresh or reopen the same URL.

Application repositories keep their own PR, review, and release rules. This documentation repository, its branches, and its pull requests are public. Keep customer information, secrets, internal catalogues, and project evidence in approved access-controlled locations. Assign a guide owner, keep version and review records, and use Git history to recover earlier versions.

Requirement language

  • Must: You must meet this requirement before release when the section applies.
  • Should: Follow this default unless you document why another safe approach is appropriate.
  • May: Optional.
  • Direct commands: Use, Require, Do not, and Never also mean must, unless the point explicitly says it is conditional, should, or may.

  • Application entry points and production commands.

  • Dependencies, imports, model calls, agent frameworks, tools, and MCP/plugins.

0.3 Apply the relevant guidance

  • Every project: Apply business correctness, code quality, configuration, secrets, identity, data protection, privacy, client portability, testing, deployment, monitoring, and recovery guidance.
  • AI or agentic project: Start with Step 11, then apply the AI evaluations in Step 18.
  • Shared multi-tenant project: Apply tenant isolation across identity, data, queues, caches, memory, vectors, reporting, support, and operations.
  • Browser or cookie-based project: Apply trusted-host, CORS, CSRF, secure-cookie, session-expiry, logout, and browser security-header guidance.
  • Sensitive or regulated data: Apply stronger privacy, retention, deletion, provider, audit, and legal/compliance controls.
  • High-impact read, decision, or action: Start with Step 4, then apply the relevant authorization, testing, and audit and recovery controls.
  • Files, OCR, or RAG project: Apply file validation, malware, parser, extraction-confidence, retrieval-permission, and knowledge-freshness guidance.
  • Graph, Teams, email, or webhook project: Apply the matching integration guidance.
  • Worker, scheduled, or WebSocket project: Apply the runtime guidance in Step 14 and the durability, scheduling, and WebSocket guidance in Step 15.
  • Agent deployed through Agent Factory autodeployment: Declare the prerequisites in Step 0.4 and prepare the handoff package in Step 24.

Important: Do not report a missing technology pattern when the project does not use that technology. Also do not skip authentication, authorization, configuration, tenant validation, tests, or monitoring merely because the project is small or deployed for one client.

Rate each issue using the approved Skysecure risk matrix. If a central matrix is not available, document the project's method and get approval from the responsible security, privacy, and business roles where needed. A delivery team must not informally approve its own exception.

Do not release while a Critical or High risk remains in security, privacy, safety, legal or compliance obligations, tenant isolation, data integrity, or important business results. Fix or technically contain the problem, reduce the remaining risk below High, and verify the result again.

In this guide, client means the customer receiving the solution, Entra tenant means the identity directory issuing users and tokens, and application data tenant means the boundary used to isolate records, files, queues, memory, and search data.

0.4 Declare autodeployment prerequisites

Applies when: The agent is deployed through Agent Factory autodeployment into a client's Azure tenant.

The deployment owner must be able to install the agent without a developer present. During development, list all required mailboxes, identities, permissions, and settings, including anything the platform does not already provision. Give this list to the deployment owner before release.

  • Declare each mailbox and business-access role separately. Do not use one generic "email access" requirement. For an invoice agent, the PO mailbox, invoice mailbox, finance approvers, and agent service/sender mailbox are separate requirements. State what each role can do and whether it is required for core operation, required only for an enabled feature, or optional.
  • Define the Azure Table fields and rules. The deployment owner sets up a dedicated Azure Table for that client's deployment. Give each declared role its own named column. Document the keys, column names, data types, validation rules, and format for multiple values. Read the account, table name, and configuration from deployment settings; do not put client values in code. Clearly separate each tenant, agent, and environment.
  • Collect the client's real values during installation. After deployment, the client's verified Global Admin completes the required setup fields. Use the common agent setup for multiple optional Agent Admins, multiple allowed users/groups, sender mailbox, multiple report recipients, send time, and time zone. Keep these separate from the agent's business-role assignments.
  • Block use of incomplete required roles. Never use a guessed, blank, default, or partially configured identity. Until required core setup is valid, allow only the authorized setup/recovery path and block business processing. Missing settings for an optional feature block that feature. Optional admins and user restrictions remain optional; an explicitly saved organization-wide access mode follows the common setup rules.
  • Verify permissions, not only entered values. An Azure Table entry does not grant Entra roles, Azure RBAC, consent, mailbox access, or sending permission. Declare the exact required permissions separately, arrange the approved grants, and validate identity and effective access before the dependent operation is enabled.
  • Do not use Power Platform custom connectors for these autodeployment email or RBAC-style integrations. Record the approved integration and permission mechanism in the handoff package.

STEP 1 — DEFINE THE REAL BUSINESS FLOW

Before writing code, describe how the solution will work from beginning to end.

Write down:

  • Who starts the workflow.
  • Where the input comes from.
  • Which users and systems are involved.
  • What the agent reads, creates, updates, sends, or approves.
  • Which system holds the official version of each important record.
  • What successful completion means.
  • What happens when information is missing, invalid, duplicated, late, or contradictory.
  • What can be corrected, cancelled, retried, or manually completed.
  • Which actions require a human decision.
  • What the user or client will see at every stage.
  • Which use cases are intentionally unsupported.

Convert every important business requirement into an acceptance test. The implementation, documentation, tests, and client explanation must describe the same workflow.

A healthy production flow

Most production agents follow this general flow, with unnecessary steps removed for simple synchronous use cases:

Input or trigger
    ↓
Authenticate and bind the trusted tenant/user context
    ↓
Authorize the requested operation
    ↓
Validate schema, size, limits, and business identifiers
    ↓
Create a durable operation record and prevent duplicates
    ↓
Process with deterministic rules and AI only where useful
    ↓
Validate and authorize the final action again
    ↓
Call the approved external system or tool
    ↓
Record the result, notify users, monitor, and reconcile failures

STEP 2 — CHOOSE THE SIMPLEST SAFE ARCHITECTURE

  • Separate entry points, business rules, integrations, storage, and AI/tool logic.
  • Keep APIs and event handlers lightweight. They should validate, authorize, call a service or workflow, and return a response.
  • Keep business logic independently testable without starting the complete web application.
  • Define the inputs, outputs, formats, and behaviour that APIs, events, tools, webhooks, queues, and stored data must follow.
  • Save important records and workflow progress outside the running application so they are not lost when it stops.
  • Assume that containers and processes can restart at any time.
  • Plan for multiple copies of the application (replicas) processing work at the same time.
  • Set limits on each workflow. Do not allow endless loops, tools repeatedly calling themselves, or agents calling each other without limits.
  • Add a framework to coordinate work only when you need multiple routes or agents, pause/resume handling, saved progress checkpoints, or human approvals.
  • Do not expose internal agents or privileged tools directly to external callers.
  • Record important architecture decisions and why the selected design is safe.

You should be able to replace an application process or container without losing important business records. Use the destination's duplicate-prevention feature (idempotency) when available so a repeated request does not repeat the action. If you do not know whether an external call succeeded, show that status and check what happened before retrying.

Before coding, draw how data moves and where identity or access checks happen. Create a practical threat model: explain what could go wrong with identities, tenant boundaries, untrusted input, external data processors, AI/tool access, privileged actions, sensitive data, and outbound destinations.

For each important threat, record what is at risk, the planned safeguard, how you will verify it, the remaining risk, the owner, and the target date. Use the approved risk process for any accepted remaining risk, with a responsible approver and an expiry or review date. Update this record after significant changes to the architecture, permissions, models, tools, or integrations.

Build once for the business; keep the AI approach replaceable

Mandatory developer standard: Keep each new agent's business logic separate from its Copilot, Foundry, or open-source implementation. Switching the AI approach must not mean rewriting the same business rules. Keep AI-specific changes in a small, clearly named group of modules. Two or three files is a useful goal where practical—not a fixed limit, and not a reason to skip other required changes or tests.

  • Separate the user channel from the AI approach. Microsoft 365 Copilot and Teams are the intended user-facing channels across the three approaches. Keep their entry points separate from the AI implementation. Channel authentication, manifests, and platform-specific capabilities may still need different integration code and validation.
  • Keep the same business behaviour. For the same agent, keep validation, access rules, tenant isolation, approvals, duplicate prevention, persistence contracts, and report rules independent of the AI provider. Reuse email, storage, and other integration components when their contracts are unchanged. Do not scatter Copilot-, Foundry-, or model-specific SDK calls through business methods.
  • Give business code one clear way to call AI. Call a function or interface owned by your application, such as ask_ai(), instead of calling a provider directly from a business workflow. Define how inputs are checked, what context may be sent, the result format, and what happens on failure. Implement this interface separately for each approach and connect the selected implementation at startup. Keep permission checks and final business decisions outside the model. A provider response must not skip those checks.
  • Keep approach-specific changes together. Isolate the provider client, prompts or orchestration, and startup wiring in clearly named modules. Document additional changes to configuration, dependencies, tests, manifests, permissions, hosting, or deployment resources. Do not compress unrelated responsibilities into two or three files just to meet a count.
  • Keep environment and approach separate. Development/production selection chooses the correct environment settings; it does not by itself convert Copilot to Foundry or open source. Select the approved provider through trusted configuration or the repository's startup wiring. Reject invalid required settings and do not silently switch to an unapproved provider.
  • Each approach repository must deploy on its own. Include all application source, list its dependencies, and provide the required platform files and packages. Its own standard pipeline must be able to build, test, and deploy it. Organizing code into folders does not require another repository, a pipeline per folder, or another running agent service. A shared package is optional.
  • Apply shared fixes to all relevant repositories. Copies of common code do not update automatically. Record which modules are shared and which reviewed version each repository uses. Apply relevant business and security fixes to every supported approach. Record its tests and release status separately. Updating one approach must not silently change another production deployment.
  • Prove every supported approach. Run the common business/security tests and the approach's own integration, AI-behaviour, channel, and end-to-end tests. Check malformed model output, unavailable providers, authorization, tenant isolation, and duplicate-sensitive actions. A successful conversion or pipeline alone is not evidence that all approaches behave correctly. Do not claim support for an approach that has not been implemented and validated.

Invoice example: Keep PO/invoice matching, finance permissions, SharePoint records, PDF generation, and daily-report rules unchanged when their requirements are the same. Route AI requests through ask_ai(); its Copilot implementation talks to the approved Copilot service, its Foundry implementation talks to the configured Azure model, and its open-source implementation talks to the approved hosted model. Replacing the language model does not automatically replace Azure document extraction or Microsoft 365 integrations; treat those as separate changes when required.

Developer handoff: Document the common contract, reusable modules, approach-specific files, configuration and dependency differences, and conversion-test evidence. Apply this separation pattern to every agent, but do not copy invoice-specific business rules into unrelated agents or build unused provider frameworks in advance.

STEP 3 — WRITE MAINTAINABLE, MODULAR, PRODUCTION-READY PYTHON

Core coding rule: Another developer should be able to find a business rule, see what it depends on, test it separately, and understand how it behaves in production without reading the whole repository.

In this step:

  • Naming · Structure · Design principles · Python practices · Module boundaries
  • Docstrings · Configuration · Logging · Dependencies and automation · Review readiness

No single design rule proves that code is good. SOLID provides useful questions for object-oriented design; it is not a Python requirement or a quality certificate. If design advice conflicts, use this order:

  1. Protect correctness, security, privacy, and data integrity.
  2. Prefer the clearest design that satisfies the real requirement.
  3. Keep related work together and make dependencies visible so the behaviour can be tested.
  4. Keep business rules in one place without joining unrelated parts of the system.
  5. Add ways to extend the code only when there is a real or well-supported need.

This follows Python's focus on readable, practical code in PEP 8 and PEP 20. Use design principles to help make decisions, not just to say that you followed them.

Follow one clear naming language

A name should tell another developer what something means, what it does, and which part of the system owns it. Use the same approved business terms in requirements, code, APIs, events, storage, prompts, logs, and documentation.

Link each repository to the current Skysecure domain glossary and name its owner. If the glossary does not exist yet, record Unknown — owner — target date in Step 0. Do not claim that automated naming checks passed, or create conflicting terms in different projects.

Other code and systems may depend on your API fields, environment variables, events, queues, prompt IDs, resource names, and stored fields. Treat these names as contracts and use a documented compatibility or migration process to change them. You may rename internal Python code normally when tests prove that its behaviour has not changed.

Agent repository names: Use the same naming pattern as the organization README:

af-{layer}-{business-name}-agent-{approach}
  • Layer: Use be for backend or fe for frontend.
  • Business name: Describe what the agent does, using lowercase words separated by hyphens.
  • Approach: Use copilot, foundry, or opensource.

Example: af-be-invoice-processing-agent-copilot. Replace the business name and approach for your agent; do not copy the invoice name into an unrelated project.

The .github, governance, and shared platform repositories have different purposes and do not need this agent naming pattern. Repository owners must document approved exceptions. Existing -cron repositories keep that suffix until their code is combined with the main agent and the change is validated.

Logical service names: A service or worker inside a repository can use the following pattern. This is not a replacement for the agent repository name above:

<domain>-<capability>-<component>

Examples: billing-reconcile-agent, intake-email-worker, document-render-api.

  • Use lowercase words separated by hyphens.
  • Select business-domain and capability terms from the approved glossary.
  • Choose a component name that describes the main part you deploy, such as api, worker, scheduler, agent, ui, or infra.
  • For logical services, add an organization or portfolio prefix only when the approved naming catalogue requires it. Agent repository names always follow the af- pattern above unless an exception is approved.
  • Do not include a client, tenant, environment, region, employee name, version, or temporary words such as new and final.
  • Do not rename an existing repository or released resource merely to satisfy a newer convention. Record the preferred name and migrate through an approved plan only when the operational benefit justifies the risk.
  • If a repository contains several parts that can be deployed, document what each part does, which identity it uses, its production start command, and which parts are released together.

  • Never encode a client, tenant, environment, or secret value into the variable name.
  • Keep an already released variable stable or support a documented transition before removing it.

Organize code by what it does and what it depends on

Use the existing repository structure when it is already clear. Do not reorganize a working codebase only to match a template. For a new installable Python service, prefer a src layout so tests exercise the installed package instead of accidentally importing a working-tree copy. This is the layout recommended by the Python Packaging User Guide and pytest.

   domain rules     application-owned port
                              ↓
                Graph / SharePoint / DB /
                  model / email adapter
  • Keep main.py, app.py, or bootstrap.py focused on startup and shutdown: load checked settings, set up logs/metrics/traces, create shared resources, pass services to the code that needs them, and register routes and other entry points.
  • Entry points validate and authorize input, call one application use case, and translate its result. They do not contain business workflows or direct database/SDK calls.
  • Domain code contains business rules and the conditions that must always stay true. It must not import FastAPI routes, cloud SDK clients, database sessions, or deployment settings.
  • Application code puts the workflow steps together. Use small interfaces owned by the application when an external service must be replaceable or tested separately.
  • Adapters connect those interfaces to provider SDKs. Keep the provider's request formats, pagination, retries, and error handling in the adapter.
  • Pass dependencies through constructors or function parameters. Do not construct network clients, repositories, credentials, or model clients inside business methods.
  • Use a class when related operations genuinely share dependencies or lifecycle state. Use a plain function for stateless parsing, validation, mapping, calculation, or formatting; a class is not automatically more production-ready.
  • Make it clear which code calls or changes external systems. Where practical, keep parsing, normalization, comparison, calculation, validation, and mapping in pure functions: they return a result without changing outside data.
  • Keep __init__.py files lightweight. Do not perform network calls, load secrets, construct clients, or start work during module import.
  • Do not keep request, user, tenant, workflow, or mutable business state in module-level globals.
  • Avoid circular imports, wildcard imports, runtime sys.path changes, and catch-all utils.py, helpers.py, or manager.py modules that collect unrelated behavior.

Keep closely related work in the same module, and avoid unnecessary dependencies between modules. This is what high cohesion and low coupling mean. Microsoft recommends the same approach: keep business knowledge together and connect components through clear APIs (Azure Architecture Center).

Apply design principles deliberately

  • KISS — keep the design simple: Choose the least complicated design that meets the current business, security, reliability, and scale requirements. Simple does not mean skipping validation, tests, observability, or failure handling.
  • Separation of concerns: Separate request handling, permission checks, business decisions, workflow coordination, data storage, provider calls, and user-facing output when they change or fail for different reasons.
  • DRY — do not repeat business knowledge: Keep one official definition of each rule, schema, mapping, or policy. Do not combine unrelated code just because a few lines look alike. A little repeated code is safer than making unrelated features depend on each other. This is the original intent of DRY.
  • YAGNI — do not build speculative capability: Do not create plugin systems, generic factories, optional workflows, or configuration flags for requirements that do not exist. YAGNI does not justify postponing security, tests, logging, recovery, or maintainability work. See Martin Fowler's original YAGNI explanation.
  • Composition over inheritance: Build behaviour by connecting objects or functions with clear responsibilities. Use inheritance only when the child can safely replace the parent without changing the behaviour callers rely on.

Use SOLID as five review questions, not five mandatory layers:

  • Single Responsibility: Does this part of the code have one clear job, with one main business reason or responsible business role that would require it to change?
  • Open/Closed: Is there a real need to add a variation without rewriting stable business rules? Do not add an abstraction for imaginary future changes.
  • Liskov Substitution: Can one implementation replace another while keeping the same promised behaviour, required conditions, error meanings, and external effects?
  • Interface Segregation: Does the caller depend only on the small set of operations it needs, instead of a large provider or service interface?
  • Dependency Inversion: Does business code use an interface owned by the application, with startup code supplying the actual SDK or infrastructure adapter?

Do not add extra code just to look like you follow SOLID. Avoid an interface for every class, a class for every function, factories that only wrap one constructor, inheritance used only to reuse code, or many files that only forward calls. These can make a workflow harder to follow. The author of SOLID also describes the principles as guidance, not rigid rules (Robert C. Martin).

Use a typing.Protocol only when you need to define a clear interface or swap one implementation for another. In the example, startup code selects and connects the actual services; this startup location is called the composition root:

from typing import Protocol


class DocumentStore(Protocol):
    """Provide the document operations required by the use case."""

    async def get(self, document_id: str) -> Document | None:
        """Return one document, or None when it does not exist."""


class ProcessDocument:
    """Process one document using explicitly supplied collaborators."""

    def __init__(self, store: DocumentStore, matcher: Matcher) -> None:
        self._store = store
        self._matcher = matcher

    async def execute(self, document_id: str) -> MatchResult:
        """Return the match result for an existing document."""
        document = await self._store.get(document_id)
        if document is None:
            raise DocumentNotFoundError(document_id)
        return await self._matcher.match(document)

processor = ProcessDocument(

For a simple local helper, call the function directly or pass a callable. Do not add a protocol and factory when they only make the code harder to follow. Python's Protocol checks the required structure; an implementing class does not have to inherit from it (Python typing documentation).

Write clear, typed, predictable Python

  • Follow one automated project style based on PEP 8. Choose one formatter and one import/lint configuration; do not spend reviews debating manual formatting.
  • Give modules, classes, functions, variables, events, and exceptions names from the business domain. Avoid vague names such as data, item, do_work, process, or manager when a precise name exists.
  • Type all new production function and method parameters and return values. Gradually strengthen legacy modules rather than adding broad Any annotations only to silence the checker.
  • Prefer Sequence, Mapping, Iterable, or a small protocol for inputs if the code does not need one specific container type. Use a specific return type when the code guarantees that type.
  • Use Any only when necessary. Check unknown data and determine its type before passing it to business logic.
  • Type hints do not check values at runtime. Validate external API data, events, files, model output, configuration, and stored payloads when they enter a part of the system that trusts them.
  • Use typed models for incoming/outgoing data and named objects for business values. Do not pass dictionaries with unclear fields through many layers.
  • Use enums or constrained literals for closed state and mode values. Reject unsupported values rather than silently defaulting.
  • Avoid mutable default arguments, shared mutable class attributes, and functions whose name suggests a read but secretly writes state.
  • Use datetimes that include a time zone, and specify the business time zone where needed. Pass a clock into time-dependent business code so tests can control the time and get repeatable results.
  • Represent money with the approved exact domain representation, such as integer minor units or Decimal; never use binary floating point for financial decisions.
  • Use context managers for files, locks, transactions, and other resources with cleanup requirements.
  • Raise specific domain or integration exceptions with safe messages. Preserve the cause with raise ... from exc when translating an exception, and catch it only where a real recovery, translation, retry, or final failure decision can be made.
  • Remove dead code, commented-out alternatives, copied experiments, unused feature flags, and duplicate implementations before merge. Version control is the history.
  • Keep generated reports, local databases, caches, telemetry, temporary files, coverage output, and IDE artifacts out of source control.

Split code by responsibility—not by an invented line limit

Python has no official maximum line count for every function or file. A short file can still depend on too many unrelated things. A longer module can be easy to maintain if it handles one clear responsibility. Use size and complexity to decide what needs review, not as proof that code is good or bad.

Split a function, class, or module when it:

  • Mixes business rules, workflow coordination, and reading or writing external data.
  • Has more than one unrelated reason to change.
  • Keeps switching between high-level workflow steps and low-level implementation details.
  • Contains deeply nested branches or many independent decision paths.
  • Makes several unrelated changes outside the function, such as writing records or sending messages.
  • Requires an unrelated set of dependencies.
  • Is difficult to name precisely or test without extensive setup.
  • Causes frequent merge conflicts because unrelated features modify the same file.

Do not split one clear operation into tiny functions that only forward calls, or into numbered files, just to reduce line count. Separate a real responsibility and give it a clear name, inputs, outputs, and behaviour.

Set up automated checks that warn when code has too many decision paths. For example, Ruff's C901 rule measures McCabe complexity and lets you set the warning limit (Ruff C901). Use the warning to review and simplify code. Code just below the limit can still be confusing. If you suppress a warning, limit the suppression to the necessary code and explain why beside it.

Write useful docstrings and comments

Follow PEP 257 consistently. Explain the expected behaviour and reasons that are not clear from the code. Do not just repeat what the code already says.

Docstrings are required for:

  • Public modules, classes, functions, and methods.
  • Application use cases, agent tools, integration ports, adapters, and important domain services.
  • Non-public code whose contract, side effects, restrictions, safety behavior, or algorithm is not obvious.

A trivial private helper with an accurate name and obvious behavior does not need a boilerplate docstring. For a non-trivial callable, document only what applies:

  • A one-line summary starting with an action, describing what the code does.
  • Meaning or restrictions of inputs when annotations and names are insufficient.
  • What the return value means, including special values such as “not found” and results that are only partly complete.
  • Exceptions callers are expected to handle.
  • Any external changes, duplicate-prevention rules, transaction requirements, permission checks, rules for simultaneous calls, and retry behaviour.
  • Conditions that must always remain true, units, limits, and the business reasons behind them.

Do not repeat type annotations, narrate each code line, or promise behavior the implementation does not provide. Update the docstring in the same change as the contract.

def calculate_total(lines: Sequence[InvoiceLine]) -> Decimal:
    """Return the exact invoice total in the invoice currency.

        MixedCurrencyError: If the lines do not share one currency.

    This function performs no network, storage, or rounding side effects.
    """
    ...

Use comments sparingly to explain why a non-obvious business, security, performance, or compatibility choice exists. Delete comments that merely translate the syntax into English. PEP 8 warns that a comment that contradicts changed code is worse than no comment.

Manage .env, .env.example, and production settings correctly

Define and validate settings in one place, with clear types and rules. Do not read settings through scattered os.getenv() calls across the application.

Define the settings and their validation rules
  • Define one typed settings schema. Load and validate it once in the startup code before accepting requests or starting a worker.
  • Do not give required production settings fake default values. Check allowed URLs, identifiers, timeouts, modes, and sizes. Also check rules involving more than one field.
  • Keep the loaded settings unchanged for the life of the process. Pass the complete settings object, or just the settings a component needs, into each service.
  • Fail startup when required configuration is missing, empty, malformed, contradictory, or unknown. Report the field and rule without printing its raw value.
  • Keep environment-variable names stable and uppercase. Do not rely on case distinctions because Windows environment keys are case-insensitive.
  • Keep ordinary defaults safe. Never default authentication off, tenant checking off, TLS verification off, unrestricted CORS on, or a production dependency to a developer endpoint.
  • Do not dump the environment or serialize the complete settings object into logs, tests, health endpoints, or error responses.
Use typed settings at runtime

For FastAPI/Pydantic projects, pydantic-settings is a good default. It defines setting types, checks values at startup, and documents which source wins if a setting appears in several places. It is recommended, not required. Another loader is acceptable only if it provides the same results. Here is a basic example:

View the typed-settings example 
from pathlib import Path
from typing import Annotated, Literal
from uuid import UUID

from pydantic import AnyUrl, Field, UrlConstraints, field_validator
from pydantic_settings import BaseSettings, SettingsConfigDict


HttpsUrl = Annotated[
    AnyUrl,
    UrlConstraints(
        allowed_schemes=["https"],
        host_required=True,
        max_length=2083,
    ),
]


class Settings(BaseSettings):
    """Define and validate process-wide application configuration."""

    model_config = SettingsConfigDict(
        env_prefix="APP_",
        env_ignore_empty=True,
        extra="forbid",
        frozen=True,
        hide_input_in_errors=True,
        validate_default=True,
    )

    environment: Literal["development", "test", "staging", "production"]
    log_level: Literal["DEBUG", "INFO", "WARNING", "ERROR", "CRITICAL"]
    log_format: Literal["console", "json"]
    tenant_id: UUID
    external_service_url: HttpsUrl
    request_timeout_seconds: float = Field(default=30, gt=0, le=120)

    @field_validator("external_service_url")
    @classmethod
    def reject_url_credentials(cls, value: HttpsUrl) -> HttpsUrl:
        """Reject credentials embedded in a configured service URL."""
        if value.username or value.password:
            raise ValueError("URL credentials are not allowed")
        return value


def load_settings(dotenv_path: Path | None = None) -> Settings:
    """Load settings, using a dotenv file only when explicitly requested."""
    return Settings(
        _env_file=dotenv_path,
        _env_file_encoding="utf-8",
    )
  • In this example, a local launcher may call load_settings(Path(".env")).
  • In this example, tests construct settings explicitly or call load_settings(None) after controlling relevant environment variables.
  • In this example, a deployed service calls load_settings(None) and receives values from its deployment platform. Whichever approved loader is used, production must explicitly disable dotenv discovery and must not search for or depend on a repository .env file.
  • With Pydantic's default non-CLI source order used by this example, process environment takes priority over .env. Keep the selected order documented and tested if the project enables CLI settings or customizes its settings sources.
  • If settings must report a validation error, exclude input values from diagnostic output. Validation errors may otherwise contain the supplied value.
  • A typed HTTPS URL validates syntax, scheme, host presence, and the absence of embedded credentials in this example; it is not a destination allowlist. Validate the host and port against the approved integration configuration and enforce the outbound controls in Step 13.

For this non-CLI example, the source behavior documented by Pydantic Settings is: initializer values take priority over process environment, process environment takes priority over .env, and _env_file=None disables dotenv loading. Enabling CLI settings or customizing the sources can change the complete order.

Keep developer and deployment files aligned

Use the files as follows:

  • .env is an optional developer-local file. It may contain local credentials and must never be committed or used as the production configuration source.
  • .env.example is the safe settings reference committed to Git. List every supported variable once. Explain its purpose, type, units, and allowed values using safe examples. Leave secrets and client-specific values blank.
  • Deployment configuration supplies non-secret values through the hosting platform or an approved configuration service and supplies secrets through managed identity and an approved secret store.

Supply Azure production configuration safely

For Azure-hosted production:

  • Prefer workload identity so you do not need to store an application credential. In production, select the credential type matching the hosting design, such as ManagedIdentityCredential for Azure managed identity or WorkloadIdentityCredential for workload federation. Locally, explicitly select an approved developer credential. A broad chain that tries several credentials in production may choose an unexpected identity (Azure Identity credential-chain guidance).
  • Keep credentials, API keys, passwords, and connection strings in Azure Key Vault. Keep endpoints, feature settings, and ordinary configuration in platform settings or Azure App Configuration. Key Vault is not a general configuration store (Microsoft Key Vault guidance).
  • Read complete endpoints, the cloud's identity authority, deployment names, any managed-identity client ID, and tenant/environment values from settings. Do not build public-cloud URLs using suffixes fixed in code. Other Azure clouds and client environments may use different values.
  • Do not change process-wide environment variables to hold the tenant for an individual request. First identify the tenant from trusted information, then load its settings. Keep each tenant's cached settings separate.
  • A masked type such as SecretStr reduces accidental display; it is not a vault and does not prevent downstream code from revealing the value.
  • Unit tests must not read a developer's .env, Azure CLI session, or live Key Vault. Test missing, blank, invalid, and unknown settings, and which source wins when values conflict. Test at least two fresh tenant configurations.

Build logging as code—not scattered print statements

Configure logging once

Use Python's standard logging API throughout application code and keep the backend replaceable.

  • Each module defines logger = logging.getLogger(__name__) once.
  • The application configures handlers, formatters, filters, and levels once at startup, preferably with logging.config.dictConfig() and disable_existing_loggers=False.
  • Domain, service, route, adapter, and reusable library modules must not call basicConfig(), add their own handlers, or change the root logger.
  • Use print() only for intentional command-line user output. Server and worker diagnostics belong in the logger.
  • Send container logs to standard output/error and let the platform collect, retain, and rotate them. Do not let multiple processes write independently to the same local file.
Use levels consistently
  • DEBUG: Detailed diagnostic context useful during investigation; still contains no secrets, raw personal data, or unrestricted payloads.
  • INFO: Normal service and business events: startup, accepted work, an important status change, completion, and planned shutdown.
  • WARNING: Something unexpected or suspicious happened, service quality dropped, a retry is needed, or a problem was recovered from, but the service can continue.
  • ERROR: An operation failed and the process can continue with a recorded or returned failure.
  • CRITICAL: The service cannot operate safely or an essential control is unavailable.

Validate APP_LOG_LEVEL and APP_LOG_FORMAT as separate settings. A sensible Skysecure default is readable console output with DEBUG locally, and structured JSON with INFO in deployed environments. These are team defaults, not Python rules. Debug logging must not weaken identity checks, permissions, tenant separation, validation, hiding of sensitive values, or safe error responses. Any temporary production debug setting needs approval, a time limit, an audit record, and automatic return to the previous setting.

Emit stable structured events

Use consistent event names and only approved log fields. Do not build log messages by dumping arbitrary objects:

View the structured-logging example 
import logging

logger = logging.getLogger(__name__)


async def handle_operation(command: OperationCommand) -> OperationResult:
    """Run one operation and emit safe lifecycle events."""
    logger.info(
        "operation_started",
        extra={
            "event_name": "operation_started",
            "operation_id": command.operation_id,
            "outcome": "started",
        },
    )

    try:
        result = await execute_operation(command)
    except DependencyTimeout as exc:
        logger.warning(
            "operation_dependency_timeout",
            extra={
                "event_name": "operation_dependency_timeout",
                "operation_id": command.operation_id,
                "outcome": "retryable_failure",
                "error_type": type(exc).__name__,
            },
        )
        raise

    logger.info(
        "operation_completed",
        extra={
            "event_name": "operation_completed",
            "operation_id": command.operation_id,
            "outcome": "succeeded",
        },
    )
    return result
Protect and test logging data
  • Standardize fields such as UTC timestamp, severity, event name, service/version/environment, safe request/correlation/operation reference, trace/span ID, component, outcome, duration, retry count, dependency, and stable error code.
  • Set the request and operation context when work enters the application. Use ContextVar, a filter, or a LoggerAdapter to carry it safely through async code. Reset the context when that work ends. Do not create a separate logger for each request or tenant.
  • Use parameterized logging for variable message text, for example logger.debug("matched %d records", count), instead of eager f-strings. Guard expensive debug calculations with logger.isEnabledFor(logging.DEBUG).
  • Log an exception once, in the request handler, job, queue consumer, or integration code responsible for the final result. Use logger.exception() only inside an exception handler, and only if the exception is safe to log and the log destination is protected. You must still raise the error, retry, undo or correct an action, or record failure as appropriate.
  • Never log passwords, tokens, cookies, authorization headers, private keys, connection strings, complete settings, raw prompts or model responses, resumes, invoices, emails, attachments, full request/response bodies, arbitrary provider errors, or unnecessary personal data.
  • Clean carriage returns, line feeds, separators, and control characters from untrusted log fields. Limit field length so input cannot create fake log entries or fill storage.
  • Keep diagnostic logs separate from required audit events. Ordinary APP_LOG_LEVEL changes, sampling, or a best-effort log pipeline must never suppress an audit record required for an approval, access change, financial action, HR decision, or other high-impact event.
  • Define what happens if each required audit record cannot be saved. Prefer saving the audit record, or an outbox record for later delivery, in the same transaction as the official business change so both succeed or both fail. Before a high-impact external action, save what was authorized in storage that survives restarts. After the call, record whether the outcome is confirmed or unknown, then compare with the external system to resolve any uncertainty. If you cannot save the required record before acting, block the action or save it in a durable queue. Never complete the action while silently losing its required evidence.
  • Do not make an async request wait on slow network logging calls. Send logs through a queue or batch exporter with a size limit. Document what happens during an outage or when the queue is full, and monitor lost events.
  • Test logging with captured records: level, event name, JSON/schema validity, field allowlist, correlation, absence of duplicates, redaction, CR/LF handling, context isolation, exporter failure, and shutdown flushing.

These rules follow the Python Logging HOWTO, Python Logging Cookbook, OWASP Logging Cheat Sheet, and OpenTelemetry log-correlation model. Keep application calls on standard Python logging even when an OpenTelemetry bridge is used. Verify the selected language implementation in the current OpenTelemetry Python status; any non-stable Logs implementation must be version-pinned and tested before production adoption.

Control dependencies and automate code quality

  • Use pyproject.toml as the central project and tool configuration where supported. Declare the supported Python version and align the formatter, linter, type checker, test runner, and runtime with it.
  • Separate runtime dependencies from development/test dependencies. Remove unused packages and justify new ones by capability, maintenance, security, license, and operational cost.
  • For deployed applications, commit the lock file produced by the approved package manager and reproduce the complete dependency environment in CI. Use hashes where supported. Do not hand-edit generated locks.
  • Run tests against the installed package or an editable install, not through ad hoc PYTHONPATH or sys.path modifications.
  • Use one approved tool for each job. A practical Python baseline is Ruff for formatting/linting, mypy or Pyright for static typing, pytest for tests, and the approved security/dependency scanners. Equivalent approved tools are acceptable; running several overlapping tools without a purpose is not.
  • Configure rules in the repository and pin tool versions. Do not enable every available lint rule blindly, and do not weaken rules globally to silence one difficult file.
  • For every noqa, type: ignore, skipped test, coverage exclusion, or suppressed scan finding, limit the exception, explain why it is needed, and name its owner. Keep it available for review. Include the specific rule or error code where supported.
  • Measure branch coverage to reveal untested decisions, but do not treat any universal percentage as proof of quality. Test important behavior, error paths, state transitions, and security boundaries.
  • Add a regression test for every bug fix so the same bug is caught if it returns. Unit tests must run independently and give repeatable results. Use integration tests for real adapters, contract tests for agreed interfaces, and a small number of end-to-end tests for critical workflows.

Local development and CI must run the same pinned commands. For example:

python -m ruff format --check .
python -m ruff check .
python -m mypy src
python -m pytest

The repository should expose one documented command that runs the approved equivalent of the complete code-quality gate. A change is not complete when it works only from an IDE or only on the author's machine.

STEP 4 — MAKE BUSINESS RULES AND STATE CHANGES EXPLICIT

  • Define each possible record status and which status changes are allowed.
  • Reject a status change that is not allowed. Do not silently move the record forward anyway.
  • Keep intake, processing, AI recommendation, human approval, external action, notification, and final completion as separate states when they can fail independently.
  • Validate every required identifier and business field.
  • Route missing, uncertain, contradictory, or low-confidence critical information to the documented manual-review, quarantine, or safe-rejection path. Never guess or silently pass it.
  • Use fixed, testable code rules for money, permissions, legal rules, fixed thresholds, and other known business checks. Do not let a model invent these decisions.
  • Never let model confidence replace a required business validation.
  • Never let a model silently change the official input just to make a validation check pass.
  • Preserve corrections and history instead of overwriting the evidence of what happened.
  • Handle duplicate requests, amendments, cancellations, retries, late events, and out-of-order events intentionally.
  • Keep the evidence needed for important decisions, without collecting more than necessary: a protected input reference or keyed digest (a fingerprint made using a secret key), validation result, rule/model version, final decision, actor, and time. If integrity checks require a content hash without a key, protect that hash too. It may identify the underlying data; do not assume it is anonymous.

Human control for high-impact actions

Every high-impact action needs an approved authority model. Where law, policy, or risk requires human approval for a payment, hiring decision, legal action, access change, deletion, deployment, external communication, or other material action, apply all controls below:

  • Show the reviewer exactly what will happen, including the target and effect.
  • Link approval to a version of the proposed action that cannot be changed, or to a collision-resistant digest that reliably identifies that exact action.
  • Make approval one-time and time-limited.
  • Record who approved it and when.
  • Reject the approval if the action changes after approval.
  • Recheck identity, tenant, authorization, policy, and current state immediately before execution.
  • Prevent the agent or requester from approving its own action when separation of duties is required.
  • When the risk requires one person to request and another to approve (maker-checker), require an extra identity check and an independent approver or approval channel.
  • Keep AI recommendations clearly separate from the final human decision.

Approved automation based on fixed code rules may act without a human approving every operation, but only within documented limits. It must have only the permissions it needs, separate conflicting duties, keep audit records that survive restarts, support stopping and recovery, and be reviewed regularly. A model response alone never gives permission for a high-impact action.

STEP 5 — REVIEW AI-GENERATED CODE AS AN UNTRUSTED DRAFT

AI can help you write code faster, but you are still responsible for the result: its design, correctness, security, performance, and ease of maintenance.

  • Read and understand every generated or changed line.
  • Use only organization-approved AI development tools, accounts, models, extensions, and data-handling modes.
  • Do not submit credentials, production payloads, client documents, personal data, confidential architecture, or restricted source code unless that exact tool and use are approved for the data classification.
  • Give an AI development tool only the repository, command, network, cloud, and external-system access required for the task. Keep production deployment, permission grants, material deletion, and change approval inside the normal human-controlled process.
  • Inspect the complete diff for unrelated changes, removed safeguards, unsafe defaults, and duplicated code.
  • Verify packages, SDK methods, configuration names, permissions, and platform behavior against the version actually used by the project.
  • Verify the origin, licence, maintenance status, security, and approval of generated dependencies or copied code. A plausible package, API, or citation is not evidence that it exists or is suitable.
  • Write tests from the requirement and risk, not only from the generated implementation.
  • Do not accept code that disables authentication, validation, scans, type checks, or failing tests simply to make the build pass.
  • Do not keep fallback code that silently bypasses a missing dependency or security control.
  • Require an independent review for identity, permissions, sensitive data, financial or HR logic, destructive actions, and infrastructure.
  • If the developer cannot explain how the code works and fails, it is not ready to merge.

STEP 6 — EXTERNALIZE AND VALIDATE CONFIGURATION

Portability rule: The same reviewed code and build should work in development, staging, Skysecure, and approved client environments. Put environment differences in validated settings and deployment automation.

  • Never put environment- or client-specific values directly in code. This includes tenant IDs, client IDs, resource IDs, domains, SharePoint sites, mailboxes, list/library names, storage accounts, databases, model deployments, regions, callback URLs, schedules, and client-specific currencies or policy limits. Keep security, financial, and business rules that do not vary in fixed, version-controlled, tested code. Use checked, versioned settings only for behaviour that genuinely differs.
  • Use one typed and documented configuration system.
  • Document each setting, its purpose, type, allowed values, safe default, whether it is required, whether it is sensitive, and whether it is tenant-specific.
  • Validate application settings such as required values, URLs, ranges, limits, timeouts, retention, and feature flags before the process accepts work. Validate infrastructure settings such as replica ranges, resource limits, networking, and scaling rules through infrastructure tests, deployment policy, and production smoke checks before traffic promotion.
  • Stop startup when required security or identity configuration is invalid. If an optional feature is misconfigured, disable that feature safely and make the problem visible.
  • Keep local reload tools and sample users out of production. Development mode must not disable authentication, authorization, tenant isolation, validation, duplicate protection, or required business and data-integrity rules.
  • Maintain separate configuration for each environment.
  • Treat prompts, model selection, retrieval settings, tool definitions, feature flags, permissions, routing, and business thresholds as behavior-changing configuration.
  • Version, review, test, and deploy behavior-changing configuration through the same protected process used for code.
  • Record a fingerprint that identifies the configuration without revealing secrets, both with the release and in runtime monitoring data.
  • Keep a tested way to restore the previous approved configuration.
  • Detect production settings that differ unexpectedly from the approved configuration.

Move from development to production without code changes

Mandatory for every agent: Use the same application code and release artifact in dev and production. Select the environment once; deployment must supply the matching configuration automatically. Developers must not edit code or manually switch a list of settings for each release.

Use APP_ENVIRONMENT as the single environment setting, following this guide's APP_ naming convention:

Environment settingConfiguration supplied by deployment
APP_ENVIRONMENT=developmentDev resources, test data, test mailboxes, and dev identities and secret references.
APP_ENVIRONMENT=productionApproved production resources, live mailboxes, and production identities and secret references.

One selection, not one total setting: During client setup, the deployment owner must create or configure the resources and connect the right settings and secret references to each environment. Later releases reuse this setup. Changing APP_ENVIRONMENT alone does not create resources, move data, or grant access.

  • Validate in one place. Read the setting through the shared typed configuration system. Reject missing, blank, or unsupported values before accepting work. Use development and production; test and staging are also supported when needed, with isolated resources and the same protections. Resource-name codes such as dev and prd are not runtime values. Migrate existing variable names through a documented transition, not competing selectors.
  • Load the correct configuration. Keep variable names consistent; deployment supplies their environment-specific values and secrets securely. Validate them against the intended client and deployment target. Stop on missing or inconsistent required configuration; never silently switch to mock services, in-memory storage, or another environment.
  • Keep environments separate. Dev identities must not access production data or secrets. Test emails, queues, storage, and external actions must stay inside approved test resources. Never switch a live production deployment to development mode to run tests.
  • Keep the same security and business checks. Authentication, permissions, tenant isolation, validation, duplicate detection, and data-integrity rules must remain enabled in every environment. Debug logging must not expose sensitive data.
  • Apply the selection to every component. The main app, workers, and scheduled Container App Jobs must receive the correct environment configuration. Keep their identities separately scoped to the permissions each component needs.
  • Prove it before release. Test both environment configurations, invalid selections, missing dependencies, and wrong-environment resource mappings. Exercise production mode using approved isolated acceptance-test resources and identities, then promote the same tested artifact with the production configuration. Record the results; a setting alone is not proof of production readiness.

Example — repeated invoice uploads: Use synthetic invoices in dev. Confirm that a duplicate does not repeat business actions or send another email. To repeat the full workflow, create a fresh test case or reset only the isolated dev test records with an approved test tool. Do not disable duplicate protection or clear production records.

Developer handoff: Keep the supported values, configuration mapping, safe test-data reset procedure, and test evidence in the repository. The deployment owner selects the target environment; no application source changes are required.

Before calling an agent portable, deploy it into a clean client-like environment using only documented configuration and automation. Source-code changes for a new tenant or client are a design failure unless the client has a genuinely different product requirement.

STEP 7 — PROTECT SECRETS, KEYS, AND CREDENTIALS

  • Prefer managed identity or workload identity over stored credentials.
  • Keep unavoidable secrets in an approved secret manager such as Azure Key Vault.
  • Never put secrets in source code, sample environment files, tests, prompts, logs, traces, screenshots, deployment output, container images, or generated documentation.
  • Never send tokens, credentials, database connection strings, or signed access URLs to a model.
  • Separate credentials by environment and tenant when the isolation model requires it.
  • Give each identity access only to the secrets it needs.
  • Keep a list of secrets showing who owns each one, which components use it, why it is needed, when it expires, and when it was last replaced.
  • Alert before a certificate, key, or credential expires.
  • Make rotation possible without source changes or long downtime.
  • Test normal and emergency rotation.
  • Use approved platform cryptography and maintained libraries for encryption, signing, hashing, and random values. Do not design a custom cryptographic scheme or weaken certificate validation.
  • Scan source history, build artifacts, images, and logs for exposed secrets.
  • Revoke an exposed credential immediately. Removing it from the latest commit is not enough.

STEP 8 — AUTHENTICATE, AUTHORIZE, AND MINIMIZE PERMISSIONS

Identity rule: Authentication tells the system who is calling. Authorization decides what that caller is allowed to do. Both are required for protected operations. Any anonymous endpoint must be explicitly approved, narrowly limited, rate-controlled, and unable to expose protected data or perform a protected action.

Use a supported authentication library or platform middleware. Apply the checks required by your authentication method. Use a supported validator for tokens, signatures, and certificates where available. If none exists, follow the provider's published rules, use approved cryptographic functions, test with the provider's official test cases where available, and get an independent security review. Never invent your own encryption or signature method.

  • OAuth/OIDC-protected API: Accept an access token meant for this API, never an ID token as permission to call the API. Check the signature and allowed algorithm using trusted metadata, including support for signing-key changes. Check who issued the token (issuer), which API it is for (audience), its tenant and validity times, the calling application or authorized party, required scopes or application roles, and the expected user/application identity type. See Microsoft's access-token validation guidance.
  • Interactive browser or native sign-in: Use the supported authorization-code flow with PKCE, exact allowlisted redirect URIs, and validated state and nonce where applicable. Do not introduce the implicit flow for a new application.
  • mTLS: Check the trusted certificate identity or its approved identity mapping, certificate validity, revocation policy, and certificate replacement. If a proxy handles TLS, accept client-certificate information only from an approved proxy whose identity has been verified.
  • API key: Do not use an API key alone for sensitive, privileged, or high-impact user authorization. Scope, expire, rotate, revoke, rate-limit, protect, and safely compare each key.
  • Webhook: Apply the provider's complete signature, token, or client-state contract, freshness window, and replay protection. Provider-specific requirements in Step 13 also apply.

Then enforce authorization:

  • Deny access by default.
  • Authorize every API, command, record, file, report, queue operation, and agent tool on the server.
  • Check record ownership and tenant scope, not only the caller's general role.
  • Separate read, write, approve, and administration permissions.
  • Check permissions again immediately before the tool runs or the action is performed.
  • Never rely on a hidden button or disabled UI control for security.
  • Distinguish actions performed as a user from background actions performed by the application.
  • Use delegated or on-behalf-of access when an action must occur as the user.
  • Use application permissions only when the action is intentionally performed as the application without delegated user authority, and the service identity and operation are explicitly approved. If a user initiated the wider workflow, authenticate and authorize that user at the responsible boundary and ensure the application-only downstream call cannot broaden the approved action.
  • Give Microsoft Graph, SharePoint, mailbox, storage, database, and model identities only the permissions required by the feature.
  • Review permissions periodically and remove unused access.
  • Use separate workload identities when privilege, trust boundary, environment, or lifecycle differs—for example production deployment versus runtime processing.
  • Require approved multi-factor authentication (MFA) for privileged admins and people approving production deployments or high-impact actions. Require phishing-resistant authentication for privileged Entra roles and whenever the risk assessment says it is needed. Enforce this through the identity provider or protected approval process. Require a fresh extra identity check when the action's policy demands it, and keep proof of the successful check without recording secrets. Manage emergency-access accounts separately, alert when they are used, and test access and recovery without weakening normal rules. Follow Microsoft's current administrator authentication-strength guidance.

Never use model output or an editable request field as proof of the tenant ID, user ID, role, or permission scope. Use verified identity claims and approved server-side mappings to decide who the operation runs for and what it may do.

Standard agent setup: owner, administrators, access and reports

Mandatory developer standard: Build this setup into every new SkySecure agent, whether it uses Copilot, Foundry, or open source. The client may choose not to add extra Agent Admins or restrict users, but developers must still implement these options. Allow multiple Agent Admins, allowed users or groups, and report recipients—not just one person.

  • Initial setup: The client's verified Global Admin completes onboarding and nominates the agent's primary owner. Verify setup authority through trusted identity and permission checks, not a typed email address. Keep at least one authorized owner and a controlled recovery process.
  • Optional additional Agent Admins: Allow the owner to nominate multiple department admins or other responsible people. They receive the same in-agent setup and administration controls as the owner, within that tenant and agent only. This does not grant Entra Global Administrator, Azure administration, or unrestricted access to confidential records. Allow each admin to be added or removed individually. The agent must work when no additional admins are provided.
  • Select who can access the agent: Provide a multi-select list for allowed organization users or groups, with individual additions and removals. When restrictions are selected, only those users or group members can use the agent; keep a separately authorized administration path for its owner and Agent Admins. Check access on the server for chat, APIs, tools, files, and reports, not only in the screen. Other signed-in users should see: "You don't have access to this agent. Please contact your organization's Agent Admin or IT team." Do not return protected data or run the requested action.
  • User selection is optional: If no restriction is selected during initial setup, all signed-in internal members of that organization can use the agent. Clearly show "All signed-in members of your organization can use this agent" before saving, and store this as an explicit access mode. This does not include anonymous users, other tenants, or guests by default. An empty restricted list, missing setup, invalid configuration, or a failed permission lookup must not open access to everyone. Changing restricted access to organization-wide access requires an explicit authorized admin choice.
  • Keep trusted identity and data permissions: Entra sign-in and token validation remain required; the Azure Table access list does not replace them. Email addresses can be used for selection, but resolve and store the trusted tenant and Entra user/group object IDs. Agent access never overrides record ownership, department boundaries, approval rules, or confidential-document permissions.
  • Save and apply admin changes: Save settings in Azure Table, separately for each tenant, agent, and environment. Only authorized admins can change owners, admins, access rules, or report settings. Validate changes, prevent users from granting themselves higher access, and prevent simultaneous edits from overwriting each other. Keep an audit history. Document and test how quickly access changes and removals take effect. Block protected actions if permission cannot be confirmed.
  • Optional daily reports: Follow the Jobs, ReportLab, and Microsoft Graph standard. When reports are enabled, collect these settings during agent setup and allow authorized admins to update them later:
    • Send from: The mailbox or email address the report should be sent from. Verify that the sending identity has permission to send from that mailbox; entering an address alone does not grant permission.
    • Send to: One or more recipient mailbox or email addresses. Support multiple recipients, allow individual additions and removals, validate and deduplicate the addresses, and check that each recipient is permitted to receive the report's data.
    • When to send: The local send time and a valid time zone such as Asia/Kolkata.

    Keep the Agent Admin list, allowed-user/group list, and report-recipient list separate. Adding a recipient must not grant agent or admin access, and allowing someone to use the agent must not automatically subscribe them to reports. Keep reporting disabled until its required settings and sending permissions are valid.

  • Apply the saved schedule: Use Azure Container Apps Jobs for daily report workers. Saving a time in Azure Table does not update the job by itself. Build code that updates the job, retries failures safely, and checks the saved time against the actual job schedule until they agree. Show pending, applied, or failed status; do not show success before the job is updated. Convert local time to the job's UTC schedule, including daylight-saving changes where needed. Check current settings before sending, prevent duplicate daily delivery, and follow the scheduled-work rules.
  • Prove it before release: Test setup with optional fields omitted, multiple admins and allowed users/groups, individual additions and removals, allow and deny cases, the denial message, wrong-tenant access, data permissions, revoked admins, and failed configuration reads. Test the configured sender mailbox and denied sending permissions, delivery to multiple permitted recipients, recipient removal, time-zone and schedule changes, retries, and duplicate prevention in an isolated non-production environment.

Govern non-human identities through their full lifecycle

Applies when: An agent, API, worker, scheduled job, tool adapter, deployment pipeline, or external integration authenticates without a human user.

Every identity used by an application or job needs an owner, an approved purpose, only the required permissions, and a safe process for removing it.

  • Maintain an approved identity inventory in the repository or central platform registry. Record the logical identity, environment, tenant model, purpose, technical owner, business owner, authentication method, permission scopes, high-impact capabilities, last review, risk-based review cadence or next-review date, and retirement method.
  • Keep credentials, tokens, private certificates, and secret values out of the inventory. Portable repositories should describe desired identity and permission intent; live tenant-specific principal and resource IDs belong in protected deployment inventory or trusted infrastructure outputs.
  • Compare the documented identities with the actual Azure resources, Entra app registrations and service principals, managed identities, federated credentials, Graph permissions, and role assignments. Block release if an identity has gained unapproved permissions, unless an approved emergency exception is still within its time limit.
  • Separate identities when the trust boundary, environment, permission set, or lifecycle differs. Do not create a new identity merely for every file, class, or process without a real boundary.
  • To isolate read-only work from privileged actions, put the privileged identity in a separate runtime, worker, or service that checks identity and permissions before granting access. Giving two identities to the same process does not protect one from the other if that process is compromised.
  • For Azure-hosted workloads, choose a system-assigned or user-assigned managed identity according to lifecycle, replication, preauthorization, audit, and intentional sharing requirements. For external CI/CD such as GitHub Actions, prefer workload identity federation. Use certificates only where federation is unavailable, and use client secrets only as an approved, monitored, time-limited exception.
  • Separate development, test, staging, and production identities. Production pipelines must trust only the intended repository and protected branch, tag, or deployment environment.
  • Review high-impact and write-capable identities more frequently. Detect and alert on overdue access reviews as well as sign-ins, permission changes, unusual token use, failed authentication, inactive identities, and approaching credential expiry.
  • Test credential rotation, permission removal, emergency revocation, and recovery without source-code changes.
  • If an identity loses its owner, quarantine or disable it after impact assessment and notify the responsible teams. Delete it only through controlled offboarding after dependencies are confirmed.
  • For client tenants, document the enterprise application, approved tenant, required consent, Graph application roles or delegated scopes, tenant-administrator actions, and revocation process.

STEP 9 — PROTECT TENANT AND CLIENT BOUNDARIES

Tenant rule: In a dedicated client deployment, reject users and applications from any tenant that is not explicitly approved. If a support or management tenant is approved, document why it needs access. Give it only the required permissions, limit the access period where practical, and keep a complete audit record.

For a shared multi-tenant service, carry the trusted tenant and user context through every layer:

  • Database queries and uniqueness rules.
  • Storage containers, object paths, and file access.
  • Queue messages and background jobs.
  • Caches, sessions, locks, and rate limits.
  • Agent memory and workflow checkpoints.
  • Vector-store writes and retrieval filters.
  • Reports, exports, analytics, and search.
  • Logs, traces, support tools, and administrative portals.

With each queued task, save trusted details of who requested it and why it was allowed: actor type, identity and tenant IDs, requested operation, permission basis, creation time, and expiry. Do not put access tokens in queue messages. Access may be removed after a task is queued, and scheduled or application work may have no user. Check current permissions and policy again before the worker takes a sensitive action.

Use tenant-aware keys and server-enforced filters. Do not query broadly and filter the result only in application memory.

Test that one tenant or user cannot read, search, modify, delete, export, or infer another tenant's data. Include caches, files, vector results, reports, support tools, and error messages in these tests.

Support access should be time-limited, approved when appropriate, fully audited, and limited to the necessary client and task. Never give support users unrestricted access to every tenant.

Automate client setup and removal. Check licenses, consent, resources, permissions, data schemas, subscriptions, connectivity, and capacity. Setup must be able to resume if only some steps succeed. When removing a client, stop new work, finish or cancel queued tasks, revoke identities, remove subscriptions, delete retained tenant data according to policy, and confirm that access has ended.

STEP 10 — PROTECT DATA AND PRIVACY

For every data type, know why it is collected, where it comes from, where it is stored, who can access it, how long it is kept, how it is deleted, whether it is backed up, and which region or provider processes it.

  • Before handling personal or regulated data, record which countries' or regions' rules apply and what they require. Record the approved purpose and legal basis where required, who decides how data is used and who processes it, contract instructions, required privacy notices or consent, and the responsible privacy or legal owner.
  • Complete and approve a privacy or data-protection impact assessment when required by law or policy, or when the processing is likely to create high risk. Review it after a material change to the purpose, data, model, provider, automation, retention, integration, or affected population.
  • Collect only the data needed for the approved workflow.
  • Encrypt sensitive data in transit and at rest.
  • Restrict access using least privilege.
  • Do not use production client data in development. An exception needs a documented reason and approval, only the minimum data, equivalent access and retention protections, and proof that anonymized data cannot realistically be linked back to people. Replacing names with IDs or using reversible masking still leaves personal data that must be protected. Prefer realistic, artificially created test data.
  • Define retention and automatic deletion for documents, prompts, responses, memory, vector data, traces, logs, reports, dead-letter records, and backups.
  • Pause normal deletion only when an authorized legal or records hold requires data to be kept. Record which data is covered, who authorized the hold, who may access it, its review date, and when it ends.
  • Support required export, correction, and deletion processes.
  • Apply sensitivity labels and data-loss prevention where required.
  • Confirm the approved data-use purpose, training use, retention, residency, deletion, subprocessor, security, incident-notification, and contractual terms for every external processor that receives data—including model, OCR, guardrail, MCP/plugin, tool, telemetry, storage, and support providers where used.
  • Document any cross-border or regional movement of data.
  • Keep secrets, full documents, raw prompts, and unnecessary personal information out of logs and audit records.
  • Prefer protected references, fingerprints made with a secret key, and decision details with sensitive values removed. Avoid copying the sensitive data itself. A normal hash of predictable personal or business data can still reveal what it represents; protect it instead of treating it as anonymous.
  • Protect audit records from unauthorized access and modification.

STEP 11 — CONTROL MODELS, PROMPTS, MEMORY, AND TOOLS

Applies when: The project uses an AI model, RAG, tools, agent memory, autonomous behavior, or multiple agents.

Core AI rule: Code must verify identity, check permissions, separate tenants' data, enforce business rules, and check approvals. Never rely on the model to enforce these protections.

In this step:

  • Orchestration · Prompts · Untrusted AI content · Context · Guardrails
  • Model validation · Custom models · Tools · Autonomy and memory · Responsible AI

Manage the AI workflow from startup to retirement

  • Before release, add the AI system to the approved central AI inventory. Record its owner, purpose, users, risk level, model/provider/version, data types and regions, tools and permissions, affected people, human oversight, evaluations and safeguards, deployed environments, next review, incidents, and retirement plan. Update this record after important changes. Follow a planned process to retire the system and its related files and resources. See the NIST AI RMF Govern playbook.
  • Keep prompts, routing rules, workflow definitions, tools, and output schemas version-controlled and testable instead of scattering them through request handlers and business code.
  • If the framework provides a reusable compiled workflow or graph that is safe to share, create it once per process during application startup. Do not store request, session, user, tenant, or memory data inside that shared object.
  • If a required workflow cannot be initialized, fail startup or readiness clearly. Do not hide the problem by rebuilding it inside each request.
  • Use fixed code rules to route exact commands, policy decisions, and privileged actions. Use a model to choose a route only when interpreting meaning is genuinely needed. Check the selected route before running it.

Version, test, and release prompts like code

Keep production prompts that affect model behaviour in a controlled, versioned location. Do not hide them as scattered strings inside request handlers.

  • Store prompts in the repository or an approved prompt registry. It must keep released versions unchanged, control access, keep an audit history, require evaluations before release, support promotion and rollback, and separate environments.
  • Give each prompt family a stable identifier and keep its version as a separate field. Record its owner, purpose, risk level, compatible models and supported settings, input contract, output schema, evaluation suite, and change reason.
  • Store these details in a format tools can read and validate: a metadata block at the top of the prompt file (frontmatter), or a manifest beside it. A prompt registry must provide the same fields. CI must reject a released prompt if required details are missing or do not agree.
  • When prompts are repository-backed, prefer a discoverable convention such as prompts/<agent>/<purpose>.v<n>.md. Use <agent>.<purpose> as the stable prompt ID and v<n> as its separate version; when one combined artifact reference is needed, use <prompt_id>@<version> consistently.
  • Never edit a released prompt version. If behaviour changes, create a new version and keep the previous approved version available for rollback.
  • Record the exact prompt file's digest with the release and model-call monitoring data. This lets you trace an evaluation or incident to the prompt that ran. Protect this identifying metadata; do not assume a digest makes the data anonymous.
  • Build prompts through one typed component that rejects missing or unexpected variables. Put untrusted values in clearly labelled data fields. Escaping, separators, and character normalization help format input and add checks, but they do not stop prompt injection by themselves.
  • If normalization changes untrusted content, keep the original evidence. Record what changed when it affects an audit or the ability to reproduce the result.
  • Never let request content supply a file path or unrestricted prompt identifier. When workflow selection is required, map an authorized business operation to an allowlisted prompt on the server.
  • Client-editable content may be included only as labelled, bounded, untrusted context. It must never become a system instruction, tool policy, authorization rule, or prompt template.
  • Never render secrets, tokens, connection strings, signed URLs, internal credentials, or unnecessary personal data into a prompt.
  • Use synthetic or properly redacted examples in prompt artifacts and evaluation fixtures. Real client data requires an approved purpose, access boundary, privacy treatment, and retention period and must not be embedded permanently in a reusable prompt template.
  • Before release, compare the old and new prompt on the approved evaluation set. Review task quality, security behavior, structured-output validity, cost, latency, and relevant subgroup performance.
  • Test important prompt changes in staging, then release them through a controlled rollout. Before release, define how much a result may worsen and when to roll back.
  • Re-evaluate prompts when the model, model version, tool contract, retrieval configuration, output schema, or guardrail policy changes.
  • Keep raw prompt and completion capture disabled by default. Where approved for diagnosis, redact it, restrict access, sample it, bind it to the correct tenant, and apply short retention.

Treat AI components as untrusted

  • Treat user prompts, emails, documents, websites, OCR text, retrieved chunks, model memory, tool descriptions, tool results, and model output as untrusted.
  • Treat system prompts as trusted, version-controlled behavior configuration whose integrity is protected. Also treat them as potentially discoverable: never place secrets in them or rely on them as a confidentiality or security boundary.
  • Keep untrusted content clearly separated from application instructions.
  • Plan for malicious instructions in user input, external content, saved content, images or other media, and messages from other agents. These are direct, indirect, stored, multimodal, and cross-agent prompt injection.
  • Prompt wording, delimiters, sanitization, and content filters are useful defense-in-depth, but they do not replace code-level controls.

Engineer the model context deliberately

Choose the model's input deliberately. Do not send all available data just because the model can accept it.

  • Define a context policy for each workflow and supported model. Budget system instructions, tool schemas, retrieved content, conversation state, tool results, user input, reserved output, and a safety margin.
  • Use the tokenizer and limits of the selected model. Organization-wide numbers and examples are starting points, not universal limits; approve final values from workflow evaluations, expected document sizes, latency, and cost.
  • Enforce the final model-specific budget immediately before every model call. If the assembled input exceeds it, apply the documented narrowing, summarization, rejection, or manual-review path; passing a unit test is not a substitute for the runtime check.
  • Authenticate and authorize before retrieving documents, memory, tool results, or tenant data.
  • Build a context manifest containing the prompt and policy versions, model configuration, source and document versions, chunk identifiers, retrieval and ranking configuration, trust classification, token counts, and trimming decisions needed for safe diagnosis or reproducibility.
  • Given the same recorded inputs, assemble the final model context in a repeatable way. Do not assume retrieval, changing indexes, external tools, or model-generated summaries will always return the same result.
  • Keep instructions separate from untrusted user input, documents, OCR text, memory, retrieved content, and tool results. For each important context item, keep its source, tenant, age, permissions, and history of where it came from.
  • Define which content is retained, summarized, dropped, narrowed, or rejected when a budget is exceeded. Never silently remove information required for a business decision.
  • If required input is too large, use an approved workflow to extract needed data, split it into chunks, retrieve relevant parts, process parts and combine results (map-reduce), narrow the scope, or request manual review. Do not simply cut off the extra input.
  • Treat model-based summarization, extraction, ranking, or classification used during context assembly as a separate model call. Authorize and bound its inputs, apply the required input controls, validate its output, preserve tenant and data-handling rules, and only then allow the result into a later model's context.
  • For every tool result shown to a model, document and enforce a size limit in the appropriate unit: items, bytes, characters, or tokens. Define what happens if the limit is exceeded. Return only the needed fields in a small typed response. Do not pass raw HTML, base64 content, stack traces, or full provider responses unless the use case explicitly needs a safely parsed form.
  • If full content must be stored, protect it with tenant authorization, encryption, non-guessable references, expiry, data classification, and retention controls. Do not create a new sensitive-data store merely to preserve debugging convenience.
  • Keep approvals, identifiers, decisions, and workflow status in structured official records. Conversation summaries may help the model, but must never replace those records.
  • For workflows using conversation history, document how much history is kept, when it is summarized, which summarizer and version are used, which facts must remain, which official records the summary references, and when the original conversation is kept or deleted.
  • Emit redacted structured telemetry when content is summarized, truncated, or dropped. Do not place the removed content itself in logs.

Check AI input and output in stages (guardrails)

Applies when: A model consumes untrusted content, produces user-visible content, recommends a material decision, or can call a tool.

Use this control order:

Authenticate
    ↓
Authorize the requested tenant, data, and operation
    ↓
Validate the request and, when present, quarantine, scan, and safely parse files
    ↓
Retrieve only authorized data
    ↓
Assemble bounded, provenance-aware context
    ↓
Run required input and document guardrails
    ↓
Call the model
    ↓
Run required output guardrails
    ↓
Apply deterministic schema and business validation
    ↓
Recheck authorization at the action boundary
    ↓
Execute the approved tool or external action
  • Select guardrails from the workflow threat model, data classification, user impact, language, region, provider support, latency, and cost. Not every agent requires every available detector.
  • Choose a guardrail and version from the approved Skysecure security/AI catalogue, or record a reviewed exception. Link each repository to the catalogue and name its owner. If the catalogue does not exist yet, record your chosen safeguard and version and get explicit security/AI approval. Do not claim catalogue compliance. Check that it supports your actual languages, regions, models, file sizes, response-time needs, and data-handling rules; a product name alone does not prove this.
  • File malware controls, quarantine, and safe parsing happen before extracted content is assembled or sent to a model. Input guardrails may then cover size and schema validation, direct and indirect prompt injection, topic policy, harmful content, and required personal-data handling.
  • Output guardrails may cover harmful content, unauthorized data, personal-data redaction, protected material, citations, and groundedness where the chosen service supports them. Structural output-schema validation belongs to the deterministic validation stage shown below the guardrails.
  • Detection services can miss problems or flag safe content. Passing a guardrail never grants access, proves an answer is correct, approves a business decision, or gives permission to run a tool.
  • Define whether detected personal data is allowed, redacted, tokenized, blocked, or sent to review. Workflows such as recruiting and invoice processing may legitimately require approved personal or financial information.
  • Version thresholds, categories, policies, exceptions, and provider configurations and include them in the release configuration fingerprint.
  • Define what each workflow does if a check fails or is unavailable. Normally, block high-impact actions. A low-risk information-only workflow may use an approved restricted mode. Never silently skip a required guardrail because it is unavailable.
  • Run only independent checks within the same stage concurrently. A required input guardrail must finish before the model call; an output guardrail can run only after output exists.
  • If a decision is cached, bind it to the trusted tenant, content digest, guardrail version, policy version, relevant context, and expiry. Never cache an authorization decision as a guardrail result.
  • Log the decision, policy version, category, severity, and trace ID, but not the flagged content. If investigators need to link related events, use a fingerprint made with a secret key or a protected reference that does not reveal the content.
  • Use human review for blocked content only when the business has approved the process and access, encryption, privacy, and retention controls are in place.
  • Record provider limitations and test the languages, regions, models, content lengths, and document types used by the real workflow.
  • For each workflow and policy version, measure guardrail availability, response time, cost, timeouts/errors, and how often it allows, blocks, redacts, or sends content for review. Name an owner to review safe content wrongly blocked, unsafe content missed, block reasons, and bypass attempts. Set the review frequency based on risk and usage. Version and evaluate every adjustment before using it.

Validate model behavior

  • Use structured, schema-validated output for production decisions and tool arguments.
  • Reject missing fields, unknown fields, invalid types, unsupported values, and unsafe destinations.
  • Use deterministic code for known rules and high-impact decisions.
  • Never allow a model to override a failed business, security, or authorization rule.
  • Never pass raw model output directly into shell commands, code execution, SQL, file paths, URLs, HTML, email headers, access rules, or privileged APIs.
  • Verify important claims against approved sources when factual accuracy matters.
  • Keep citations or source history when users need to understand where an answer came from.

Govern custom and fine-tuned models

Applies when: The project trains, fine-tunes, imports, or self-hosts a model or adapter. Using a managed provider's unchanged hosted model does not require a training pipeline.

  • Approve and record the base model, exact version, source, licence, intended use, limitations, and provider terms.
  • Record where training data came from, who owns it, its license or approved purpose, sensitivity, required consent or privacy basis, retention period, preparation steps, and quality review. Before training, check for secrets, prohibited data, deliberate contamination, duplicates, and important imbalances in the dataset.
  • Keep training, tuning, validation, and final evaluation datasets separate as required by the approved test design. Do not let benchmark or release-test data enter tuning inputs.
  • Version the training code, dependencies, base model, dataset manifest or protected digest, settings, tokenizer, adapters, checkpoints, and final artifact. Restrict and audit access to data, weights, and checkpoints.
  • Scan imported artifacts with approved controls, verify origin and integrity, and release only the approved immutable artifact. Compare it with the approved baseline for quality, security, privacy, safety, cost, and latency before controlled rollout.
  • Model weights, checkpoints, tokenizers, loaders, adapters, and remote model code may execute code when loaded. Treat them as software dependencies that need security checks. Prefer formats that cannot execute code and loaders with restrictions. Never load an untrusted pickle or enable untrusted remote code. If custom code is needed, pin an exact unchanged revision and review it. Prepare it in an isolated environment without production credentials. Limit the model-serving runtime's identity permissions, file access, and outbound network access. A malware scan alone does not prove that a saved model is safe to load. See the warning in the official PyTorch loading guidance.
  • Maintain rollback and retirement procedures, including removal of superseded endpoints, weights, checkpoints, and retained training data according to policy.

Restrict tools and integrations

  • Maintain an allowlist of approved tools.
  • Name tools in snake_case with a precise verb and effect, such as read_invoice, create_service_request, or send_approval_email. Avoid vague names such as run, execute, query, or do_action without a business object.
  • Name agents and workflow steps in snake_case based on their specific job. Use a clear capability name for an agent and an action phrase for a step, such as triage_agent, retrieve_context, or await_human_approval. Clearly mark tools that can write data or use privileged access in the registry, so reviewers can see their possible impact without reading the code.
  • Give each tool a narrow purpose, strict input schema, fixed or allowlisted destination, and least-privileged identity.
  • Run tools that execute code or shell commands, browse arbitrary sites, control computers, or have similar power in an isolated environment separate from the API and AI reasoning process. Prefer a temporary environment for each use. Do not pass permanent credentials into it; grant only limited, short-lived access when needed. Restrict file access, outbound network access, processes, run time, CPU, and memory. Stop the whole process tree, validate the outputs, and audit every call. Follow Microsoft's AI-agent sandboxing and egress guidance.
  • Validate tenant, user, authorization, target, amount, path, and business rules inside the tool boundary.
  • Do not let the model create tools, add MCP servers, select credentials, widen permissions, or change approval policy.
  • Use an approved registry for MCP servers, plugins, and external tools.
  • For every registered external tool or server, record its owner, exact version, approved data classes and purposes, destination and processing regions, retention and deletion behavior, training or secondary use, subprocessors, contractual approval, permission boundary, and retirement method.
  • Pin or record tool/server versions, verify server identity, use authenticated transport, and review manifests and schemas.
  • Audit sensitive tool calls using redacted metadata, actor, target, protected action reference or keyed digest, decision, and outcome.

Limit autonomy, memory, and cost

  • Bound model calls, steps, tool calls, recursion, execution time, tokens, concurrency, and cost.
  • Keep user, session, and tenant memory isolated.
  • Define memory retention, summarization, deletion, and maximum size.
  • Never store secrets in memory.
  • Add a tested kill switch for the model and high-risk tools.
  • If the business workflow allows it, provide an approved limited mode for model outages or unexpected behaviour. Otherwise, stop safely and show the failure. Do not skip a check that depends on the model or pretend the work succeeded.
  • Version models, deployments, prompts, tools, retrieval settings, guardrails, and evaluation datasets.
  • Detect provider-side model changes where possible and evaluate them before continued use.

Use AI responsibly

  • Tell users when they are interacting with AI where appropriate.
  • Clearly distinguish an AI suggestion from an approved business decision.
  • Document limitations and unsupported scenarios.
  • Provide human review, correction, appeal, or escalation when decisions affect people.
  • Test harmful output, unfair treatment, accessibility, and material performance differences where relevant.
  • Keep a named business function accountable for every material AI-assisted decision process.

STEP 12 — HANDLE EMAIL, FILES, OCR, AND RAG SAFELY

Applies when: The project handles messages, documents, attachments, images, OCR, user uploads, or retrieved knowledge.

Intake and files

  • Treat every sender, message, attachment, and retrieved document as untrusted, including content from known users.
  • Validate approved senders or channels when the workflow depends on sender authenticity.
  • Before important processing starts, save a record of the received input in storage that survives restarts.
  • Move every input to a visible final or pending state such as processed, duplicate, quarantined, unsupported, rejected, failed, or manual review.

  • Run parsers with suitable isolation and resource limits.
  • Generate storage names on the server. Keep the original filename only as untrusted information with a length limit. Never use it as a file path or storage key. Encode it safely for the place where it is displayed or logged.

  • Use an approved maintained extraction service or parser suitable for the file type and risk.
  • Validate extracted data against typed schemas and business rules.
  • Record confidence for critical fields.
  • Route low-confidence or contradictory critical values to the documented manual-review, quarantine, or safe-rejection path. Never guess or silently pass them.
  • Read dates, numbers, currencies, and taxes using the correct regional formats.
  • Keep the original document and extracted result linked through protected references when audit or correction requires it.

Retrieve knowledge safely for AI answers (RAG)

  • Record source, owner, tenant, classification, version, freshness, and retention for indexed content.

Check that the design follows the provider's permission rules, such as Azure AI Search document-level access control.
  • Apply the same access rules to chunks, metadata, caches, embeddings, and citations.
  • Remove expired or revoked content from the index and caches.
  • Keep citations or source history for important answers.
  • Test malicious documents, poisoned instructions, stale information, retrieval leakage, and cross-tenant access.

Define and protect the API contract

Applies when: The project exposes a Skysecure-controlled HTTP API. Provider-managed callbacks, Teams bot activities, health endpoints, and other protocol-specific endpoints must follow their provider contract and document any justified difference.

You may write the OpenAPI specification first or generate it from FastAPI. Either way, the reviewed specification is the API contract for that release. Version or publish it with the release and validate it in CI. Keep the code, examples, client packages, and documentation consistent with it. Use Azure API Management for publication only when APIM is part of the approved design.

Design resources and representations

For client-facing domain APIs:

  • Put the major version in the path by default, such as /v1/invoices. A different versioning mechanism requires one documented service-wide decision.
  • Use plural resource nouns and lowercase hyphen-separated path segments.
  • Keep nesting shallow. Use a top-level resource with an authorized filter when deeper nesting obscures ownership or access control.
  • Use an explicit action sub-resource only when an operation is not naturally represented as resource creation or update, for example POST /v1/invoices/{invoice_id}/actions/approve.
  • Use stable external IDs that do not reveal internal details. Do not expose predictable internal keys if they let callers guess other records, learn implementation details, or bypass tenant separation.
  • Use snake_case JSON fields, UTC timestamps in RFC 3339 format, and durations with clear units. Represent money exactly, using validated decimal strings or integer minor units that follow the currency's ISO definition. Document the allowed string enum values.
  • Authorize every action and resource independently.
Use consistent status and error responses

If that later processing finds a business-rule violation, record a safe rejected or failed result as described in the API contract.

For failures generated by your JSON API, use RFC 9457 Problem Details with Content-Type: application/problem+json. Add a stable error code that client code can read and a trace ID as extra fields. Use a documented HTTPS problem-type URI on a domain the organization controls. Until that catalogue exists, leave out type and use the stable code field instead of inventing a URI naming scheme.

  "title": "Unprocessable Content",
  "status": 422,
  "detail": "All invoice lines must use the same currency.",
  "code": "INVOICE_MIXED_CURRENCY",

  • Clients branch on the stable code, not human-readable title or detail text.
  • Include instance only if it is a URI reference to this particular error occurrence, not just the affected business record. Do not reveal protected details in it. If the reference can be opened, check permissions before showing the error record.
  • Keep detail safe for the caller. Never return stack traces, credentials, queries, internal hosts, protected identifiers, or another tenant's information.
  • Use field-level error details only for safe validation feedback.
  • Keep an error-code list for APIs used by external clients. For each code, document the HTTP status, meaning, whether and when retrying is safe, and what the client must do. If an error-code change or retry-rule change breaks existing clients, handle it as a breaking contract change.

Where supported, configure the trusted gateway or ingress to use the same safe error format. Some size limits, timeouts, connection failures, and provider outages happen before application code runs. They may return the platform's own error format or no HTTP response. Document these cases and require clients to handle them. Test both gateway errors and application errors. FastAPI cannot control an error response that never passes through it.

Bound collections and trusted context

For endpoints that return a growing list, document a maximum page size and use server-driven or cursor pagination by default. Unless an existing or provider contract requires another format, APIs you own should return items, next_cursor, and has_more. A cursor must not reveal internal details and must work only for its intended tenant and query. If it contains state visible to the client, protect it against changes and give it an expiry. Allow only documented filter and sort fields, and explain the sort syntax. Use a repeatable tie-breaker so equal sort values do not change the order unpredictably. Small, stable admin datasets may use another documented pagination design.

Accept and propagate W3C trace context. Return a safe correlation or trace identifier to the caller, return Retry-After when the caller is expected to wait, and set explicit cache behavior. Use Cache-Control: no-store for sensitive or tenant-scoped responses unless an approved design proves safe caching.

Document the service's request and response headers. If you support a caller-supplied X-Client-Request-Id, use it only to link related requests, never as proof of identity, tenant, permissions, or duplicate prevention. When retiring an endpoint, publish its deprecation and migration details in the contract, the Deprecation header, and a Link to instructions. Add Sunset only when the shutdown time is known; it cannot be earlier than the deprecation time.

Get identity, tenant, role, and scope from verified authentication and approved server-side mappings. Do not trust ordinary identity fields sent by the caller. When a workflow passes between services, either check the user's permissions first and forward cryptographically protected execution details, or verify the service identity and perform the required permission check through another approved server-side method.

Those forwarded details must securely link the trusted issuer, intended audience, calling application, tenant, user or service principal, permitted operation and target, issue and expiry times, and a unique nonce or stable operation ID. Validate them at every service, reject replayed requests, and never grant more access than the original caller had. Document where user permissions are checked, and prove that direct calls or alternate routes cannot skip that check.

Version the client-facing contract before its first supported production release. If changing a path, field, type, validation rule, status, error code, security requirement, or meaning breaks compatibility, release it under an approved new incompatible contract version. With semantic versioning, increase the major version. If users need time to move, publish deprecation, migration, and shutdown plans too. Those plans do not replace the required version change.

For every owned endpoint, the released OpenAPI description must identify its purpose, authentication and authorization requirement, request and response schemas, possible status and stable error codes, and useful success and failure examples. Contract tests must cover the applicable valid, unauthenticated, unauthorized, wrong-tenant, malformed, oversized, duplicate, throttled, and dependency-failure paths; do not add meaningless cases that the endpoint cannot receive.

Enforce the contract in FastAPI

FastAPI's default validation response does not automatically follow this contract. Configure and test request models that reject unknown fields, for example with Pydantic extra="forbid". For each field, decide whether its type must match exactly or whether a safe conversion is allowed.

Also enforce media types, register exception handlers, and declare OpenAPI responses. Invalid JSON must return 400, unsupported request media types 415, and applicable schema or business validation errors 422. Your JSON API errors must use the approved Problem Details format. Keep a different response format where a provider-managed protocol requires it.

Use separate input and output models. Return a typed model through FastAPI's response_model, or explicitly check the response, convert it safely, and include only allowed fields. OpenAPI declarations describe the response but do not validate it at runtime. A raw Response or JSONResponse skips FastAPI's automatic validation and filtering. Use one only after safely converting the data yourself and testing that it follows the contract.

Exposed APIs and browser endpoints

  • Serve APIs only over HTTPS with a valid certificate. Outbound clients must validate server certificates.
  • Enforce the request-body size limit at the trusted ingress or ASGI layer before loading the whole body into memory. Count received bytes; do not trust only Content-Length. Use supported server or ingress controls to limit request-line and header size, time to read headers and bodies, keep-alive time, open connections, and simultaneous requests. Test chunked, slow, and oversized requests.
  • Reject request Content-Encoding values by default. If the API explicitly supports compressed bodies, decompress them as a stream before parsing. Limit compressed size, expanded size, compression ratio, nesting or member count, and processing time. Test compressed and chunked inputs designed to expand into excessive data (decompression bombs).
  • Validate request schemas, types, formats, ranges, lengths, body size, file size, and processing limits.
  • Enforce the declared request Content-Type before parsing and reject a missing or unsupported media type when a body is expected. Return only documented response media types and handle an unacceptable Accept contract consistently, using 406 when the endpoint supports content negotiation.
  • Reject unknown input fields and map only explicitly writable fields. Never bind caller input directly to server-owned tenant, identity, role, approval, amount, status, or audit fields.
  • Apply rate and cost limits at the relevant caller, tenant, service, and expensive-operation boundaries.
  • Use parameterized database/SDK operations and prevent SQL, command, OData, template, header, and path injection.
  • Encode untrusted output for its destination.
  • Restrict trusted hosts and CORS origins.
  • Accept Forwarded, X-Forwarded-*, and proxy-supplied certificate metadata only from explicitly trusted proxy addresses, or where network controls prove that only the trusted ingress can reach the application. The proxy must remove caller-supplied copies. Never derive identity, tenant, or authorization from these headers.
  • Protect state-changing browser requests against CSRF when cookie authentication is used.
  • Use secure, HttpOnly, and appropriate SameSite cookie settings; rotate sessions after authentication and enforce expiry, logout, and revocation.
  • Apply suitable browser security headers.
  • Return safe errors without secrets, stack traces, or internal details.

External service clients

  • Use HTTPS/TLS for network integrations, validate the certificate chain and hostname, and do not allow protocol downgrade. A non-TLS endpoint is permitted only for an approved local-only development path or a protocol and protected network design whose security review documents an equivalent control; it must never become a production fallback silently.
  • Use a supported SDK or maintained client when it provides the required behavior.
  • Reuse lifecycle-managed network clients and connection pools by destination and trust policy.
  • Use separate clients when credentials, proxy, certificate, network, or trust requirements differ.
  • Set explicit connection, read, write, and overall timeouts.
  • Validate response schemas, status codes, partial responses, and malformed responses.
  • Bound both encoded and decoded upstream response sizes, decompression ratios, and record counts before buffering or parsing. Stream where appropriate and abort and close the response on overflow.
  • Follow pagination until all records required by the business operation are collected. Never assume the first page is complete, and apply item, page, time, and cost limits to prevent unbounded work.
  • Retry only temporary failures, and only if repeating the operation is safe or verified duplicate prevention protects it. Limit retries, increase the wait between attempts, and add a random delay (exponential backoff and jitter). If an action may already have happened and repeating it could cause another change, check its outcome before retrying.
  • Respect Retry-After and provider throttling limits.
  • Where appropriate, temporarily stop calls to a repeatedly failing dependency (circuit breaking), or use an approved safe limited mode.
  • Use fixed or allowlisted base URLs and outbound destinations.
  • Never attach credentials to an arbitrary URL supplied by a user, document, tool, or model.
  • Block private, loopback, metadata, and unapproved destinations when accepting external URLs.
  • If untrusted input can affect an outbound URL, allow only required schemes, ports, and hosts. Disable redirects or check permission for every redirect destination. At connection time, validate all IPv4 and IPv6 addresses returned by DNS, and enforce outbound network restrictions. Never forward credentials to a different origin. Follow the OWASP SSRF prevention guidance.
  • Record supported API versions and monitor deprecation notices.
  • Use contract tests so provider or internal API changes are detected before production.

STEP 14 — RUN PYTHON, FASTAPI, AND SHARED RESOURCES CORRECTLY

Applies when: The project uses Python or FastAPI. Other runtimes must meet the same lifecycle, resource, health, and shutdown outcomes using supported platform patterns.

  • Keep route handlers and middleware lightweight.
  • Use async when the function performs genuine asynchronous I/O.
  • Do not block the event loop with synchronous network, database, credential, or large file operations.
  • Move unavoidable blocking work to a bounded worker/thread or separate process.
  • Use bounded concurrency. Do not create an unlimited number of tasks or threads.
  • Track every task running in the process, or manage it in a structured task group. Check all task errors. Never launch an async task and then lose track of it.
  • Reuse HTTP clients managed through startup and shutdown, and pools or factories documented as safe for simultaneous use. Create process-owned resources after a worker is forked. Follow each SDK's rules for sharing across threads, tasks, processes, and connections. If a database session, Redis pipeline or pub/sub object, or message sender/receiver is not safe to share, give each request or operation its own instance.
  • Do not create a new reusable network client or pool inside every request, tool call, or service method. Do create a short-lived session or receiver per operation when the selected SDK requires that scope.
  • Initialize resources with a clear lifecycle and close them during graceful shutdown.
  • Use FastAPI lifespan for bounded startup, initialization, and cleanup when FastAPI owns the resource.
  • Do not start uncontrolled permanent business loops inside every web replica.
  • Remember that a module-level singleton exists once per process, not once across all replicas.
  • Never use global mutable objects for user sessions, tenant context, agent memory, business locks, or workflow state.
  • Propagate request, correlation, operation, session, tenant, and workflow identifiers safely through APIs, queues, workers, tools, and external calls.
  • Use async-safe context propagation such as ContextVar where appropriate, and reset it after each request.
  • Validate configuration and initialize required resources before accepting traffic.
  • During shutdown, stop accepting new work. Finish work claimed under a lease or safely release it for another worker, then close clients cleanly.
  • In Python, use try/finally for cleanup. If asyncio.CancelledError is caught, re-raise it after cleanup unless deliberate suppression is documented, tested, and clears the cancellation state correctly. Cancel remaining tasks and await them within a bounded shutdown deadline. Follow Python's task-cancellation contract.

Keep APIs, workers, schedulers, and migrations as separate deployable components when their lifecycle, privileges, or scaling needs differ.

Provide startup, liveness, and readiness checks supported by the platform. The startup check confirms initialization. Liveness checks whether the process itself is healthy; it must not fail just because an external service is temporarily unavailable, since repeated failures may restart the container. Readiness checks whether this copy of the app can safely accept new work and may check dependencies needed to accept it. Verify these checks in the deployed environment against the platform's rules, such as Azure Container Apps health probes.

Keep health responses minimal and free of configuration, credentials, internal topology, stack traces, and sensitive dependency details. Restrict richer diagnostic endpoints to authorized operators, and bound every dependency check with a short timeout.

STEP 15 — PROCESS IMPORTANT WORK DURABLY

Durability rule: If important work continues after the response, is accepted before completion, or must resume after a restart, save it in storage that survives restarts before saying it was accepted. For work completed within the request, return success only after the official records and every promised external action are complete. If work is only queued or saved for later, return an accepted or pending response such as 202 and provide a way to check its status.

In this step: Durable processing · Messages and data stores · Idempotent writes and operations · Scheduled work · WebSockets

Durable processing

  • Use a durable queue or operation record when work continues after the response, can exceed the safe request duration, must survive process loss, or is acknowledged before completion.
  • Short work may finish within the request, but report completion only after the official records and every promised external action are complete. If an external system cannot guarantee duplicate prevention, save the intended action and any provider IDs. Record an unclear response as unknown and check the actual outcome before retrying.
  • For long-running APIs, create a durable operation and return an accepted response with a status resource or callback where suitable.
  • Give every event and business operation a stable identifier.
  • Version queue and event schemas. Keep consumers backward-compatible with messages that can remain queued during rolling deployment, replay, or recovery, and define how old unsupported messages are handled.
  • Make queue consumers safe when the same work arrives again. For external actions, use provider-supported duplicate prevention or a stable business key where available. Otherwise, save the intended action and its result. Treat a timeout or lost response as unknown, check what happened before retrying, and document any remaining duplicate risk.
  • Enforce unique records in durable storage. An earlier “does this already exist?” check alone is not enough.
  • Prefer database uniqueness rules, transactions, updates that check a condition and write in one operation, and ETags to protect simultaneous updates. If workers need a shared lease, give it an expiry, check its owner, and define renewal rules. Use fencing or version tokens to reject writes from a worker that has lost the lease.
  • Never use a Python or in-memory lock as cross-replica duplicate protection.
  • For important messages, notifications, and downstream actions, use a transactional outbox or equivalent protection: save the pending action with the business change in one transaction, then deliver it reliably.
  • Keep business completion separate from notification delivery and downstream completion.
  • Retry only transient failures and only when the action is safe to repeat.
  • Use bounded retry counts, exponential backoff, jitter, and provider retry guidance.
  • Save failure status so it survives restarts. Move work that cannot be processed to dead-letter handling, with a controlled process for trying it again.
  • Advance checkpoints only after earlier work is completed or durably queued.
  • Do not interpret a failed checkpoint read or write as "no new data."
  • Regularly compare saved work with actual results to find missing, stuck, duplicated, inconsistent, or partly completed operations. This check-and-repair process is reconciliation.
  • Test crashes, restarts, duplicates, late events, out-of-order events, and multiple replicas.

Govern message and data-store contracts

Applies when: Components exchange messages or own persisted application data.

Use names and schemas that make the business meaning and compatibility visible:

  • Name events <domain>.<entity>.<past-event>.v<n>, such as billing.invoice.received.v1.
  • Name commands <domain>.<entity>.<imperative-command>.v<n>, such as billing.invoice.process.v1.
  • Include a stable message_id, correlation_id, operation_id, trusted tenant context where applicable, schema version, occurrence time in UTC, and producer identity. Propagate trace context when supported.
  • Version schemas and keep consumers compatible with messages that can remain queued during rollout, replay, or recovery. Run old and new contracts together when a breaking migration requires it.
  • Use the provider's dead-letter capability and a controlled, authorized replay process.
  • Decide how namespaces, topics, queues, partitions, and subscriptions are separated based on tenants, regions, permissions, scale, cost, failure impact, and ownership. Do not force every client or service to use the same physical layout.
  • Name a subscription after its consuming logical service and purpose when one consumer owns several subscriptions. When a provider does not supply a dead-letter name, derive one predictably from the original destination according to the central messaging catalogue.

For owned data stores:

  • Use clear plural snake_case collection or table names and stable snake_case field names unless the selected platform has an established incompatible convention.
  • Name databases, indexes, containers, and accounts from their logical owner and data purpose using the platform's approved catalogue and technical constraints. Keep the mapping deterministic and documented; do not force a shared topology where client isolation, residency, or scale requires a dedicated store.
  • In a shared tenant-aware store, persist a trusted tenant boundary on every tenant-owned record and include it in uniqueness, partitioning, query, and index design where the real access pattern requires it.
  • Record schema version and timezone-aware creation/update times where records evolve or require audit.
  • Design indexes from measured query patterns and partition behavior. Do not force every compound index into one field order without validating the query plan.
  • Do not let one independently deployed service read another service's private store directly unless an approved shared ownership model and compatibility contract exist.
  • Create a new versioned search index if the embedding size changes, the schema becomes incompatible, or the way content is split into chunks changes. Record model and indexing versions in metadata. A keyword-only index does not need an embedding-model name.
  • In shared blob storage, begin paths with the trusted tenant boundary and use server-generated names. A dedicated deployment may instead use a separately authorized account or container when isolation, residency, or client policy requires it. Keep the original filename only as safely encoded metadata.

Prevent duplicate actions and show progress for long-running work

Applies when: An operation creates a record, changes state, sends a message, invokes an external side effect, or may exceed the caller's safe request duration.

If retrying a client-facing POST or PATCH could repeat an important business change or external action, it must accept an Idempotency-Key or use an equivalent trusted operation ID saved durably. Design PUT and DELETE with stable resource IDs so repeating them does not repeat an effect. If they cannot guarantee this, apply the same duplicate protection. Webhooks may use a validated provider event ID; queue consumers may use stable message and business-operation IDs. Document when retries are safe for other write endpoints.

  • Scope an idempotency record by trusted tenant, principal or service identity, operation, and key.
  • Reserve the key in one atomic storage operation before taking the action, so only one caller can reserve it.
  • In durable storage, save a protected digest of the request in its standard format, its current state, final status, safe response reference, and expiry.
  • Keep the record for at least the provider retry window and the business recovery window; configure the exact retention per workflow.
  • The same key and same request returns or refers to the original outcome.
  • On every repeated request, verify identity and current permissions before returning the original result. Return only fields the caller may access now. Never reuse old cookies, signed URLs, authentication headers, or other temporary security-sensitive headers.
  • For owned HTTP APIs, identify a replay through a documented response header such as Idempotency-Replayed: true without changing the original business result.
  • The same key with different input fails with 409.
  • A concurrent request returns the existing operation or a documented in-progress response.
  • Database constraints, conditional writes, downstream business keys, an outbox, or another durable control must still protect the final state. An idempotency header or earlier duplicate check alone is not enough.

Do not hold an HTTP request open when the expected or worst-case duration is unsafe for the gateway, client, dependency, or service target. Create a durable operation and return 202 Accepted:

POST /v1/documents/{document_id}/actions/process
202 Accepted
Location: /v1/operations/{operation_id}
Retry-After: 5

The operation resource should expose only safe, authorized information and use a documented state model such as:

queued → running
running → awaiting_approval | reconciling | succeeded | failed | cancelled
awaiting_approval → running | succeeded | failed | cancelled
reconciling → running | succeeded | failed | cancelled

Use one service-wide operation representation containing the operation identifier, status, creation/update timestamps, safe resource reference where applicable, optional progress, and mutually consistent result or Problem Details error fields. Omit a field only when it does not apply; do not invent a different envelope for every endpoint.

  • Scope operation access to the trusted tenant and authorized caller.
  • Do not change an operation's final status after it is complete.
  • If an external result is unclear, keep the operation open in a status such as reconciling. A lost response does not prove failure. Do not retry until checking confirms that the action did not complete.
  • Represent failure using the API's Problem Details contract.
  • Preserve enough progress to resume or reconcile after restart.
  • Define expiry and deletion.
  • Check cancellation permissions separately and explain what cancellation will do. It does not automatically undo actions already completed.
  • Use polling by default. Add callbacks, webhooks, or push delivery only when the requirement justifies their additional security and reliability obligations.

Choose the asynchronous threshold from measured service behavior and platform limits. Do not use one fixed duration for every agent.

Scheduled work

Applies when: The project runs scheduled or periodic work.

  • If a job must run once, use a managed scheduler or a design where only one elected worker owns the schedule.
  • Make scheduled jobs safe to repeat, because the same trigger can still arrive more than once.
  • Save schedules, time zones, last successful run, next run, and progress checkpoints in storage that survives restarts.
  • Alert on missed, delayed, or repeatedly failed schedules.
  • Do not run one unsafe scheduler loop inside every API replica.

For agent daily reports, implement the standard admin, access, and report setup. Azure Table holds the intended configuration; the application must reliably apply it to Azure Container Apps Jobs and confirm the result. Container Apps Jobs cron expressions use UTC, so preserve the user's local time and time zone and handle conversions, including daylight-saving changes where applicable.

WebSockets

Applies when: The project accepts WebSocket connections.

  • Use wss:// in production. For browser clients, validate the Origin header on every handshake against an exact allowlist; browser CORS policy does not protect a WebSocket endpoint.
  • Never put reusable bearer tokens, session tokens, or credentials in a WebSocket URL or query string. Browser clients must use either a secure HttpOnly session cookie with Origin checks and equivalent CSRF protection during the handshake, or a limited, short-lived, single-use connection ticket. Issue tickets through authenticated HTTPS and bind each to the expected identity, tenant, audience, and origin. Non-browser clients use a supported authorization header. Hide sensitive parts of handshake URLs and reject reused tickets. RFC 6750 explains why bearer tokens in URLs are unsafe.
  • Authenticate the connection and authorize each sensitive message or action. Revalidate long-lived authorization and close affected connections after session expiry, logout, revocation, or a material permission change.
  • Check each message's type, schema, size, and content before using it. Set per-identity and whole-service limits on connections, message rate, idle time, sessions, and resources. Slow or stop incoming work when the service cannot keep up (backpressure).
  • Save session data that must survive a restart outside the connection manager.
  • With multiple replicas, use a shared messaging backplane, a reconnect-and-resume design, or a documented method of routing a session back to the same replica.
  • Clean up tasks and connections in finally blocks. Cancel and await per-connection tasks within a bounded shutdown deadline. If asyncio.CancelledError is caught, re-raise it after cleanup unless deliberate suppression is documented and tested.
  • Test unauthorized origins, authentication bypass, connection-ticket replay, session expiry, malformed and oversized messages, flooding/backpressure, reconnect, replica loss, duplicate delivery, ordering, and resumed authorization. Follow the OWASP WebSocket security guidance.

STEP 16 — PLAN FOR SCALE, PERFORMANCE, AND COST

  • Define normal, peak, burst, and sustained workload volume.
  • Set limits for requests, files, pages, tokens, model steps, execution time, memory, CPU, and concurrency.
  • Limit simultaneous work, queue it safely, and slow or stop intake when processing cannot keep up.
  • Define what happens during overload: pause intake, reduce non-critical features, queue safely, or return an appropriate retryable response.
  • For scalable components, define minimum and maximum replicas and scale using useful signals such as queue age, depth, latency, and active work.
  • If only one instance of a component may run, enforce that rule and document how it recovers after failure.
  • Calculate calls to external services using the replica count, simultaneous work per replica, maximum calls or tool steps per operation, retries, and work that starts several parallel branches. Include every component sharing the quota. Check both steady load and bursts against Graph, SharePoint, email, model, OCR, database, storage, and other provider limits.
  • Size connection pools and queue capacity for the declared workload.
  • Prevent one user or tenant from exhausting shared capacity or budget.
  • Paginate and batch safely.
  • Cache only when useful, with tenant-aware keys, size limits, expiry, and invalidation.
  • Test normal, peak, burst, and sustained load using the intended production topology.
  • Test large and adversarial input, not only small happy-path samples.
  • Estimate expected and worst-case cost before release.
  • Add quotas, budgets, and anomaly alerts for models, OCR, storage, compute, network, autoscaling, and logging.

STEP 17 — HANDLE ERRORS WITHOUT HIDING FAILURES

  • Never use a bare except or silently ignore an exception.
  • Separate retryable failures, permanent failures, business rejection, and manual-review outcomes.
  • Return consistent, documented, structured API errors.
  • Do not return tokens, stack traces, internal paths, SQL details, or confidential data to callers.
  • Log failures with enough safe context to investigate them.
  • Preserve the original error cause when translating exceptions.
  • Do not say the work is complete until official records and every action promised by that response are complete. If later work is only saved or queued, return accepted or pending and let the caller check its status.
  • Do not convert storage, checkpoint, authorization, or configuration failure into an empty result.
  • Make partial completion visible and recoverable.

STEP 18 — TEST THE SOFTWARE AND AI BEHAVIOR

Tests should prove the real workflow and its failure paths, not merely increase a coverage number.

Software tests

Cover:

  • Business rules, calculations, validation, and state transitions.
  • Positive, negative, boundary, empty, oversized, and malformed input.
  • Missing, malformed, forged, expired, not-yet-valid, wrong-signature or algorithm, wrong-audience, wrong-issuer, wrong-calling-application, wrong-scope or role, and wrong-tenant tokens where token authentication is used.
  • Required MFA, authentication strength, and step-up behavior for privileged or high-impact human actions, including missing, weaker-than-required, stale, external-tenant, and emergency-access paths.
  • Role, permission, record ownership, and cross-user/cross-tenant access.
  • API, event, webhook, queue, file, tool, and stored-data contracts.
  • Middleware and dependency behavior and ordering, including authentication, tenant context, request IDs, CORS, error handling, rate limits, redaction, and security headers where applicable.
  • Graph pagination, throttling, token refresh, subscription renewal, and concurrency.
  • File validation, unsafe paths, archives, malware/quarantine behavior, and parser limits.
  • SQL, command, path, template, header, URL, and SSRF attempts.
  • Duplicate, retry, replay, out-of-order, and partial side-effect scenarios.
  • Multi-replica concurrency, process restart, dependency outage, timeout, and throttling.
  • Dead-letter handling, reconciliation, backup restoration, and release recovery.
  • The exact production command, port, routes, worker topology, and startup order.

AI evaluations

Applies when: The project uses any model, RAG, tool-calling, agent memory, or agent behavior.

When AI is used, evaluate:

  • Task completion and instruction adherence.
  • Correct tool selection, arguments, and use of tool results.
  • Whether answers are supported by the supplied sources (groundedness), cite the right sources, state correct facts, and avoid invented information.
  • Refusal behavior and unsupported requests.
  • Prompt injection, malicious documents, tool abuse, and data exfiltration attempts.
  • Authorization and tenant behavior.
  • Empty, malformed, slow, and unavailable model responses.
  • Cost, latency, and stability across repeated runs.
  • Harmful output, fairness, subgroup performance, and accessibility where decisions affect people.

Keep a versioned evaluation dataset covering normal, difficult, unclear, malicious, and client-relevant cases. Record its source, privacy protections, owner, known correct answers, how examples were labelled, and what it covers. Approve pass thresholds before seeing the final results. Do not lower them just to pass a release.

If AI scores the results, version the evaluator's model, prompt, scoring rules, and output schema. Compare its scores with labels from business experts and adjust the evaluation method against that reference. Measure disagreements, safe results wrongly failed, unsafe results wrongly passed, sample size, supported-language behaviour, and variation across repeated runs. AI must not be the only release decision-maker for high-impact or safety decisions. Microsoft's safety-evaluation transparency note also calls for human oversight rather than relying only on automated results.

Contract, identity, prompt, context, and guardrail evidence

Where these capabilities exist, also test:

  • API compatibility, documented status codes, Problem Details, authorization, bounded collections, asynchronous operations, cancellation, and deprecation behavior.
  • Idempotency under identical, changed, concurrent, delayed, replayed, and crash-recovery requests, including proof that downstream duplicates are prevented where the destination supports it and that ambiguous non-idempotent outcomes become visible and are reconciled before retry.
  • The declared non-human identity inventory against actual Azure and Entra permissions, assignments, federated credentials, owners, environments, and approved scopes.
  • Unauthorized workload identity use, wrong audience, wrong tenant, expired credentials, removed permissions, emergency revocation, credential rotation, and production/non-production separation.
  • That a privileged action identity cannot be reached through a model-facing or read-only runtime without passing its separate authenticated and authorized action boundary.
  • Prompt metadata, immutable released versions, missing or unexpected template variables, approved prompt selection, output-schema compatibility, and rollback to the previous approved version.
  • Old and new prompts against normal, ambiguous, adversarial, injection, data-exfiltration, tool-abuse, cost, latency, and relevant fairness cases before promotion.
  • Context size budgets, reserved output space, token counting for the selected model, oversized-input handling, source history, retrieval filtered by permissions, secure references to tool results, records of shortened content, and protection of required information.
  • That summaries cannot replace or change official identifiers, approvals, business status, or security decisions.
  • Guardrail allow, block, redact, review, degraded-mode, timeout, throttling, unavailable-provider, false-positive, and false-negative paths.
  • That a guardrail pass cannot bypass authentication, authorization, tenant isolation, deterministic business rules, schema validation, or required human approval.
  • Supported languages, regions, models, file types, and provider limits used by the real workflow.
  • The controlled rollout, monitoring trigger, kill switch, and rollback path for prompt, model, retrieval, tool, and guardrail changes.

Test discipline

  • Link important requirements and controls to tests.
  • Run affected tests and the critical regression suite on every change.
  • Run full production-like end-to-end and release tests before production.
  • Before the first release and after important changes, test a fresh client setup, expected load, switching to a backup service after failure, and recovery. Repeat these tests regularly at a frequency based on risk.
  • Run automated tests with isolated identities, resources, and representative synthetic or approved test data. Never let an ordinary test suite mutate production; keep any approved post-deployment production smoke test narrow, reversible, and clearly identified.
  • Treat critical tests as defects if they are skipped, disabled, set aside, or pass and fail unpredictably.
  • "No tests collected" is not a successful build.

STEP 19 — USE CI/CD TO PROTECT PRODUCTION

Keep source and contract history traceable

Document how your repository handles branches, pull requests, and releases. Protect every branch, tag, and deployment environment that can release software, including long-lived development and production branches. Create one short-lived branch for each task, using the same prefixes as the organization README:

feature/<task>
fix/<issue>
docs/<task>
chore/<task>

Use a short, hyphen-separated description for <task> or <issue>. Include the work-item ID when your project uses one. For example: feature/123-daily-report or fix/456-duplicate-email. Use feature/, not feat/, for feature branches.

For agent repositories, start from the latest dev, raise the PR into dev, and delete the task branch after review, merge, and dependency checks. Keep dev and any prod, test, or other environment branches still needed by the workflow. Documentation and governance repositories follow their own configured default branches; this guide uses a PR into prod.

  • Use Conventional Commit messages when release automation or changelog generation depends on them.
  • Link the pull request and final merge to the approved work item. Do not require every intermediate commit to repeat the reference when the repository uses squash merging.
  • Tag released services with an approved semantic version. Increment the major version for an incompatible supported contract—not for every internal behavior change.
  • Tag container images with immutable release and source-commit references and deploy the approved digest. Never use latest as production evidence.
  • Record breaking changes, deprecations, and required consumer migration in release notes or a maintained changelog.
  • Use CODEOWNERS to name reviewers for prompts, identity and permission code, infrastructure, production workflows, and other high-impact files. Protect CODEOWNERS itself. Enable a branch rule or ruleset that requires code-owner approval; requesting a review alone does not block a merge. Follow GitHub's code-owner protection guidance.

Enforce API and behavior compatibility

Applies when: The repository exposes a Skysecure-controlled HTTP API or owns another versioned API, event, message, tool, prompt, or stored-data contract.

For an HTTP API you own, CI must generate or retrieve the OpenAPI specification for the exact app version being built and compare it with the approved release version. For other contracts you own, compare the official schema or versioned file using that contract's compatibility rules.

  • For HTTP APIs, fail on an undocumented breaking change to a path, operation, request, response, field, type, required value, status code, security requirement, or stable error code.
  • For events, messages, tools, and stored schemas, fail on an incompatible name, field, type, required value, meaning, permission, or version change that an active producer or consumer cannot handle.
  • For prompts and other AI behavior artifacts, require an immutable new version, compatible input/output contracts, the approved evaluation comparison, and a proven rollback path.
  • For a supported contract governed by semantic versioning, permit an incompatible change only through an approved new major version. Publish a deprecation, migration, and sunset plan when consumers need time to move; that plan complements rather than replaces the version change.
  • For HTTP APIs, validate OpenAPI syntax, examples, security schemes, operation identifiers, and references; verify every external error code against the catalogue; and publish deprecation and sunset information when supported.
  • Publish only the specification, schema, or behavior artifact produced by the release artifact that passed CI.
  • Do not require API Management publication when APIM is not part of the approved deployment architecture.

Naming, OpenAPI, prompt metadata, message schema, identity inventory, and infrastructure checks count as automated release controls only after they are implemented and run successfully in CI. Until then, they remain explicit review obligations and cannot be reported as passing automation.

Protect the build and deployment pipeline

  • Protect every releasable branch and require pull requests. Make required CI and security checks merge-blocking, block force pushes and deletion, restrict bypass authority, and verify the effective rule or ruleset rather than assuming it applies.
  • Require independent review for important changes and fresh approval after material new pushes. Use GitHub's protected-branch or ruleset controls.
  • Give CI workflow tokens the minimum permissions required.
  • Run untrusted PR code only in isolated jobs without privileged access. Give them read-only repository permissions, no OIDC id-token, no protected-environment or production-network access, and no production secrets. Never check out or run untrusted code in a privileged pull_request_target or similar workflow. Treat its caches and build outputs as untrusted too. Use GitHub-hosted runners or temporary isolated self-hosted runners. Follow GitHub's current secure-use guidance.
  • Use protected deployment environments and separate build permission from production deployment permission.
  • Run applicable formatting, linting, type checks, compilation, tests, and AI evaluations.
  • Scan secrets, source code, dependencies, licenses, APIs, containers, and infrastructure where applicable.
  • For exposed services, test the running application for security weaknesses (DAST) and test API security.
  • For high-risk parsers, schemas, webhooks, and input handling, add tests using generated inputs to check rules (property-based tests) or find failures with unexpected inputs (fuzz tests).
  • For internet-exposed, shared multi-tenant, sensitive-data, or high-impact systems, get an independent penetration test before first production. Repeat it after important changes to exposed entry points, identity, tenants, privileged tools, or network boundaries. Choose the test scope based on risk and use a production-equivalent build and configuration. Fix and retest findings, and set repeat frequency from risk and client or regulatory requirements. Penetration testing is a separate assurance activity in the Microsoft Security Development Lifecycle.
  • Do not disable tests, scans, rules, or paths merely to make CI pass.
  • Pin dependencies with lock files and hashes where supported.
  • Pin base images by immutable digest for approved releases.
  • Pin or lock versions of infrastructure CLIs, providers, modules, Helm charts, and deployment tools. Generate the reviewed plan for the exact intended target state. A later tool update must not silently change what the same source deploys. If the tool can apply a saved plan, store it only in a protected location with minimum access and a short policy-based retention period; plans may contain sensitive values. Never copy plans into logs or PR comments. If a saved plan cannot be applied, check the target again and require another review if the actual deployment plan differs importantly.
  • Pin every external CI action and reusable workflow, including GitHub-owned actions, to a reviewed full-length commit SHA. Protect repository-local actions as source code and automate reviewed SHA updates. A mutable version tag is not immutable release evidence; see GitHub's action-pinning guidance.
  • Use trusted registries and protect against dependency confusion.
  • Remove unsupported dependencies before release. Replace deprecated direct and transitive dependencies within a risk-based deadline; when immediate replacement is not technically possible, record the exposure, owner, compensating controls, target date, and approved time-bound exception.
  • Generate a software bill of materials (SBOM) listing the software components included in the release.
  • Sign release files and images. During deployment, verify the signature and evidence of where and how they were built.
  • Trace every artifact to its exact source commit, dependency set, build, and configuration version.
  • Use short-lived workload identity for deployment where possible.
  • Prevent overlapping production deployments unless the rollout is intentionally designed for them.

A scan counts only when it completed successfully against the intended source or artifact and the approved ruleset. A failed, stale, partial, suppressed, or unreviewed scan does not pass.

Do not release with a reachable Critical or High security issue, missing authorization, tenant-isolation failure, active credential exposure, or an uncontrolled high-impact action. Correct or technically contain the problem and prove that the remaining risk is no longer High before release. Remediate other confirmed findings within the agreed security timeframe and verify every correction with a new scan or test.

STEP 20 — AUTOMATE INFRASTRUCTURE, CONTAINERS, AND DEPLOYMENT

Infrastructure and client setup

  • Keep one approved deployment design as the official reference, even if it includes separate APIs, workers, schedulers, migrations, and support components.
  • Provision compute, identities, permissions, networking, private access, DNS, certificates, secrets references, storage, databases, queues, monitoring, and schemas through repeatable infrastructure as code.
  • Keep environment parameters secure and separate from reusable modules.
  • When the selected infrastructure-as-code tool maintains remote state, protect it with encryption, access control, locking, versioning, backup, and tested recovery.
  • Scan infrastructure definitions and detect unexpected drift.
  • Run syntax validation and a target-environment what-if or plan before apply. Require review for resource deletion or replacement, privilege expansion, public-network exposure, and changes to stateful resources. Protect critical stateful resources with suitable deletion controls and backups, and use a separate approved process for destructive changes.
  • Run schema migrations through a controlled single-execution process.
  • Prefer expand-and-contract migrations: first add a compatible schema, move code and data to it, then remove old fields only when they are no longer needed.
  • Version migrations with the release and test them from every supported older schema using realistic data volume.   • Limit how long locks and transactions can last. Fill or update large amounts of existing data in batches that show progress and can resume after failure. Test both the migration and the approved recovery process. A migration that deletes data or cannot be reversed needs explicit review, a tested backup or other recovery method, and a check of the resulting data after deployment.
  • Make onboarding and infrastructure deployment safe to rerun after partial failure.
  • Document and verify any unavoidable client-administrator consent or setup step.

  • tenancy — for example shared or dedicated.
  • managed-by — the automation responsible for managing the resource, such as bicep or terraform.
  • repo

Use Azure Policy and infrastructure tests to check names and tags where practical. Document resource types that cannot use tags and any approved exceptions. Tags help track and manage resources. They do not check permissions or separate tenants' access.

Container and runtime safety

Applies when: The project is packaged or deployed as a container.

  • Use a maintained minimal base image.
  • Run as a non-root user.
  • Use a read-only root filesystem where practical.
  • Drop unnecessary capabilities and prevent privilege escalation.
  • Remove production debug, shell, and SSH tools that are not required.
  • Maintain a reviewed .dockerignore that excludes .git, local .env* files, credentials and private keys, virtual environments, caches, editor files, build/test output, and other development-only content that the image build does not require.
  • Keep tests versioned with every release commit, regardless of branch model, and run them during release validation. Omit them from the final runtime image unless the application genuinely requires them. If a multi-stage Docker build runs tests, copy them only into the test stage; otherwise exclude the test sources through .dockerignore.
  • Use explicit, narrow COPY instructions and inspect or scan the final image so ignored or development-only files cannot enter through a broad build step.
  • Never provide build credentials through Dockerfile ARG, ENV, COPY, command text, or ordinary build logs. Use the approved secret-mount mechanism and inspect final image metadata, history, and layers for leakage. Docker documents why ARG and ENV are unsafe for build secrets.
  • Use exec-form ENTRYPOINT or CMD; any wrapper must replace itself with the application process so termination signals reach it. Test startup and graceful termination using the final image.
  • Set CPU, memory, process, and file-descriptor limits.
  • Restrict network egress to required destinations where practical.
  • Deploy only the exact unchanged image that passed CI scans, signature checks, and checks of its build origin.
  • Keep temporary data in approved locations with size limits. Never rely on local disk for records that must survive replacement or restart.

Release and deployment

Release rule: Build once. Deploy the same unchanged release package or image to staging and production, and keep it traceable to its source and build.

  • Do not deploy production from a developer laptop.
  • Test a clean deployment in production-like staging using the real entry point, identity model, permissions, configuration, and topology.
  • Run end-to-end, smoke, identity, permission, monitoring, and recovery checks before production.
  • When risk justifies it, release to a small group first (canary), switch between two prepared environments (blue-green), or increase traffic gradually (progressive rollout).
  • Before sending full traffic, run a safe production canary or business smoke test against the deployed artifact and configuration.
  • Watch technical health and business outcomes during rollout.
  • Stop or recover when agreed error, latency, health, or business thresholds fail.
  • Keep the previous working artifact and approved configuration available.
  • Test the recovery method suited to the change: return to the previous release, deploy a corrective release, restore data, disable a feature, or stop traffic.
  • After recovery, run quick business and technical checks. Compare records and actual results for queued work, work already running, migrated data, and external actions, and resolve differences.
  • Record the final deployment, smoke-test, and reconciliation result, or record the recovery action and its outcome.

STEP 21 — OBSERVE, ALERT, AND RECOVER

Logging, metrics, and tracing

  • Emit structured logs, metrics, and distributed traces where appropriate.
  • Propagate correlation and operation IDs through HTTP, queues, workers, tools, schedules, and external calls.
  • Include service, environment, version, operation, component, and safe tenant context.
  • Never log secrets, tokens, signed URLs, complete documents, unnecessary personal data, raw prompts, or unrestricted model/tool payloads.
  • Monitor business completion as well as infrastructure health.
  • Track success, failure, pending, duplicate, retry, dead-letter, queue age, dependency latency, authorization failures, subscription health, safety failures, and manual-review rates.

Keep telemetry names stable, safe, and actionable

Use stable machine-readable event names rather than parsing changing prose. Prefer <subject>_<past-tense-event>, such as operation_started, document_quarantined, or model_call_failed.

  • Use OpenTelemetry semantic attributes where a suitable standard name exists. Pin and test the semantic-convention version used by the project before adopting evolving gen_ai.* attributes.
  • Add organization-specific fields only through the approved telemetry schema.
  • Carry trace, span, request, correlation, operation, service, version, environment, component, outcome, duration, retry count, dependency, and stable error code where applicable.
  • Use metric labels with a small, controlled set of values. Never use raw tenant IDs, user IDs, document IDs, operation IDs, URLs, prompts, exception messages, or other values that can grow without limit.
  • Use a protected mapped tenant category only when tenant-level operational visibility is approved and required.
  • Name application metrics in a stable lowercase dotted form such as <domain>.<component>.<measurement> unless the selected telemetry standard or exporter requires another mapping. Follow the selected version of the OpenTelemetry naming conventions.
  • Keep measurement units in metric metadata and use one stable metric name per signal.
  • Version dashboards and alerts when a metric or event contract changes.

For model calls, record safe metadata such as approved model/deployment version, prompt ID/version and protected prompt-artifact digest, output-schema version, token counts, duration, cost estimate, tool-call count, guardrail decision, and final outcome. Do not use unbounded identifiers or digests as metric dimensions.

When context is summarized, truncated, or dropped, emit a structured event containing the workflow and context-policy version, context slot, size before and after, number of items omitted, and overflow decision. Do not record the omitted content itself.

For guardrail decisions, record the control and policy version, decision, category, severity, workflow, and trace identifier. Store only a keyed digest or protected opaque reference when investigation requires linkage; never place flagged content in ordinary telemetry.

Monitor application and job identity sign-ins, failed authentication, permission changes, access that differs from what was approved, unused identities, and expiring credentials. Send important identity events to security monitoring and incident handling.

Monitor security advisories, deprecations, and end-of-support dates for the runtime, base image, dependencies, SDKs, APIs, models, guardrails, and other managed providers. Assign an owner and apply verified updates within the approved remediation timeframe.

Set limits on exporting monitoring data so it cannot hold up a request indefinitely. Monitor and alert when logs, trace spans, metrics, or audit events are lost. Save required audit evidence through a separate reliable path that survives restarts. Its delivery must not depend on the diagnostic log level or sampling settings.

Alerts and audit

  • Define availability, latency, success, and backlog targets.
  • Alert on customer impact, not only CPU and memory.
  • Alert on missed schedules, dead-letter growth, backup failure, certificate or secret expiry, subscription expiry, model safety issues, unusual access, and telemetry failure.
  • Give each alert an owner, severity, response action, and runbook.
  • Test alert delivery before production.
  • Keep important actions, approvals, permission changes, and security events auditable.
  • Store only the minimum redacted audit evidence needed, protect it from modification, and retain it according to policy.

Incident response and recovery

  • For the service, define incident severity levels, who responds, when to escalate, and how evidence is preserved. Define who must be notified for security, privacy, legal, regulatory, and client matters, and the deadlines for doing so.
  • Exercise the incident plan before the first high-risk release and periodically according to risk. Record gaps, owners, target dates, corrections, and retest results; follow the current NIST incident-response guidance.
  • Document how to contain an incident, isolate a tenant, revoke credentials, stop a model or tool, investigate data, communicate with clients, and restore service.
  • Turn material defects and incidents into regression tests.
  • Define the maximum acceptable downtime and data loss for important state.
  • Back up required durable data, configuration, schemas, approved prompts/policies, audit records, and tenant configuration.
  • Do not treat replication as a backup.
  • Protect backups from the application's identity. For important systems, also protect them from failures or compromise affecting the primary account, region, or other shared part of the system.
  • Test restoration into a clean environment.
  • Do not let restoring an old backup silently bring back expired or deleted data, revoked access, or data from a removed tenant. Before serving or processing restored data, reapply official deletion records (erasure tombstones), retention expiry, legal holds, revoked consent or access, and tenant-removal status. An equivalent design that keeps restores safe is also acceptable. Test this comparison and record the results.
  • Ensure recovery can recreate identity, DNS, certificates, secret references, infrastructure, queues, webhooks, and configuration where required.
  • Measure actual recovery time and data loss.
  • A recovery test that misses the approved downtime or data-loss target has failed and must be corrected before production unless the organization has formally accepted the remaining risk.
  • After recovery, check missed work and work that was already running against actual results, and resolve unfinished or uncertain operations.
